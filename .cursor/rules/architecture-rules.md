# 领域驱动设计架构规则

## 架构分层规则

项目采用领域驱动设计架构，必须遵循以下分层规则：

```
UI/表现层 -> 应用层 -> 领域层 -> 基础设施层
```

1. **领域层**：包含所有业务逻辑和领域对象
   - `models/` 目录下定义所有领域模型
   - 所有领域对象应包含自己的业务逻辑和验证规则
   - 领域对象不应依赖外部服务或基础设施

2. **应用层**：协调领域对象之间的交互
   - `services/` 目录下定义所有应用服务
   - 服务类负责协调多个领域对象和仓储
   - 服务类不应包含业务规则，只包含流程编排

3. **基础设施层**：提供技术支持
   - `repositories/` 目录下定义所有数据访问代码
   - `adapters/` 目录下定义所有与外部系统的交互
   - `utils/` 目录下定义通用工具类

4. **UI/表现层**：用户界面处理
   - `pages/` 和 `components/` 目录下实现界面
   - UI层只应调用应用服务，不应直接操作领域对象
   - UI层负责数据展示和用户交互

## 依赖原则

1. **单向依赖**
   - 内层不能依赖外层
   - 领域层不应引用应用层和基础设施层
   - 应用层可以引用领域层，但不能引用UI层

2. **依赖注入**
   - 服务类应通过构造函数接收依赖对象
   - 允许默认实例化，但必须支持外部注入
   ```javascript
   function SomeService(options = {}) {
     this.repository = options.repository || new SomeRepository();
   }
   ```

3. **接口隔离**
   - 使用抽象接口隔离不同层之间的交互
   - 通过依赖抽象而非具体实现提高可测试性

## 命名规范

1. **文件命名**
   - 模型文件：使用单数形式，如 `task.js`、`star.js`
   - 仓储文件：使用名词+repository形式，如 `task-repository.js`
   - 服务文件：使用名词+service形式，如 `star-service.js`

2. **类命名**
   - 模型类：使用大驼峰单数形式，如 `Task`、`Star`
   - 仓储类：使用大驼峰+Repository形式，如 `TaskRepository`
   - 服务类：使用大驼峰+Service形式，如 `StarService`

3. **方法命名**
   - 查询方法：使用get前缀，如 `getById`、`getTasksByDate`
   - 修改方法：使用动词开头，如 `createTask`、`updateStatus`
   - 私有方法：使用下划线前缀，如 `_formatDate`

## 领域对象规范

1. **构造函数**
   - 所有领域对象必须通过构造函数创建
   - 构造函数应处理默认值和数据类型转换
   - 不要在构造函数中有复杂业务逻辑，使用静态工厂方法代替

2. **属性访问控制**
   - 使用getter/setter控制属性访问
   - 确保数据一致性和业务规则验证
   - 不要直接暴露可变数组或对象

3. **业务方法**
   - 业务操作必须通过领域对象自身的方法完成
   - 方法应体现领域语言和业务概念
   - 避免"贫血模型"，领域对象应有行为

```javascript
// 好的例子
task.complete();
task.reschedule(newDate);

// 不好的例子
task.status = 1;
task.date = newDate;
```

## 仓储规范

1. **一致性接口**
   - 所有仓储必须继承自 `BaseRepository` 类
   - 必须实现标准CRUD接口：getById、getAll、save、delete
   - 特定查询方法命名应遵循规范，如 `getTasksByDate`

2. **数据库无关性**
   - 仓储应隔离存储细节
   - 不要在领域层或应用层直接使用存储适配器
   - 仓储方法应返回领域对象，而非原始数据

3. **批量操作**
   - 对于大量实体的操作，提供批量处理方法
   - 使用事务确保数据一致性
   - 记录详细日志，便于追踪和调试

## 服务规范

1. **职责定义**
   - 服务应负责单一领域的业务流程
   - 避免创建"上帝服务"，拒绝承担过多职责
   - 服务应通过协调领域对象完成业务

2. **事务管理**
   - 服务负责事务边界控制
   - 尽量减少事务范围，提高并发性
   - 使用事务确保多实体操作的一致性

3. **结果返回**
   - 使用标准化的结果对象格式，如：
   ```javascript
   {
     success: true/false,
     data: { ... },  // 成功时的数据
     message: '...',  // 提示消息
     error: { ... }  // 可选，错误详情
   }
   ```

## 异常处理

1. **异常捕获**
   - 仓储和服务方法应捕获内部异常
   - 详细记录异常信息，包括上下文
   - 避免向上层抛出技术性异常

2. **日志记录**
   - 使用统一的日志工具记录
   - 区分不同级别日志：info、warn、error
   - 包含足够调试信息但保护隐私数据

```javascript
try {
  // 业务逻辑
} catch (error) {
  logger.error('ComponentName', '操作描述失败', error);
  return { success: false, message: '操作失败' };
}
```

## 事件机制

1. **领域事件**
   - 使用事件总线传播领域事件
   - 事件名应使用过去时态，如 'taskCompleted'
   - 事件处理应在独立模块中实现

2. **事件订阅**
   - 事件订阅应在初始化时设置
   - 避免动态添加和删除监听器
   - 事件处理应是幂等的

```javascript
eventBus.on('taskCompleted', (task) => {
  // 处理任务完成事件
});

// 发布事件
eventBus.emit('taskCompleted', task);
```

## 性能优化

1. **缓存策略**
   - 仓储应实现适当的缓存策略
   - 提供跳过缓存的选项
   - 定期刷新或失效缓存数据

2. **批量处理**
   - 使用批量方法处理大量数据
   - 分页加载大型集合数据
   - 避免循环中单独保存实体

3. **异步操作**
   - 使用异步方法处理IO操作
   - 避免同步阻塞方法
   - 使用Promise或async/await统一异步处理

## 迁移规则

1. **兼容性**
   - 新模型必须能处理旧数据格式
   - 避免破坏性变更
   - 使用适配器模式处理格式差异

2. **并行运行**
   - 使用服务管理器支持新旧实现并行运行
   - 逐步迁移功能，避免大爆炸式替换
   - 持续验证新实现的正确性

3. **功能等价**
   - 确保迁移后功能与原有一致
   - 编写测试验证行为一致性
   - 记录并解释任何有意的行为变更

## 测试要求

1. **单元测试**
   - 领域模型应有全面单元测试
   - 测试应验证业务规则和状态转换
   - 使用mock对象隔离测试依赖

2. **集成测试**
   - 服务类应有集成测试
   - 测试主要业务流程
   - 使用内存存储适配器加速测试

3. **测试覆盖度**
   - 核心业务逻辑测试覆盖率应达到90%以上
   - 边界条件和异常情况必须有测试
   - 重构前后运行测试确保行为一致

## 文档要求

1. **代码文档**
   - 所有公共接口必须有JSDoc注释
   - 复杂算法必须有详细说明
   - 预期的异常和错误处理必须文档化

2. **架构文档**
   - 架构变更必须更新相关文档
   - 关键决策必须记录原因和考虑
   - 迁移策略和注意事项必须文档化

3. **API参考**
   - 所有服务和仓储公共方法必须在API文档中详细说明
   - 包括参数、返回值、异常和示例
   - 文档必须与实际代码保持同步
