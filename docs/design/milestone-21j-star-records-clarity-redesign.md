## 需求分析

### 功能描述

当前奖池页的 `star-records` 虽然名字叫“星星记录”，但表现更像系统内部账务流水，而不是用户能快速看懂的“星星记录”。真实代码复核后确认，页面现在的核心筛选是 `全部 / 星星获取 / 星星使用` 与 `全部时间 / 近一周 / 近一个月 / 近三个月`；这套口径把“兑换使用”“过期失效”“必做任务未完成扣除”都压扁到了同一个“使用”里，也让用户很难回答“为什么本月星星变少了”“为什么这里写本月共获得”“这批星星什么时候会过期”这些更接近真实使用的问题。

这不是视觉小修，而是信息架构与语义口径的问题。`M21J` 的目标，是在不改动星星结算主规则的前提下，把现有账务式“星星记录”收敛成一页用户能理解、且和奖池页视觉一致的“星星记录”：正式名称继续叫“星星记录”；一级筛选只保留高频路径；时间范围与展示组织明确分层，避免“最近7天”继续套用月度标题；摘要改成“获得 / 减少 / 净结果”的组合表达；单条记录用清晰标签告诉用户它属于任务获得、兑换使用、过期失效、未完成扣除，还是退回/撤销类低频变动，并把 `week / month / quarter / permanent` 这类获得记录的时效信息直接展示出来。

### 业务价值

- [x] 用户价值：用户能直接理解星星为什么增加、为什么减少、哪些是兑换消耗、哪些是过期失效、哪些是未完成扣除，以及少量退回/撤销类记录为何出现。
- [x] 技术价值：把当前散落在页面脚本与 `star-service/star-records.js` 中的筛选、分组、月汇总口径正式收敛，减少后续继续靠文案猜行为。
- [x] 业务价值：降低奖池页的认知负担，让“最近发生了什么”“当前查看区间内获得了多少”“当前查看区间内又因什么减少”在一屏内可读，并保持与奖池页一致的克制视觉体验。

### 事实基线（2026-04-15，设计前）

#### 1. 当前筛选口径是账务视角，不是用户视角

`packageMessage/pages/star-records/star-records.js` 当前初始化为：

- `selectedType: 'all'`，注释为 `all, income, expense`
- `selectedTime: 'all'`，注释为 `all, week, month, 3months`

`packageMessage/pages/star-records/star-records.wxml` 当前展示的筛选文案为：

- 类型：`全部 / 星星获取 / 星星使用`
- 时间：`全部时间 / 近一周 / 近一个月 / 近三个月`

这意味着：

- 奖励兑换、星星过期、必做任务扣星都被合并成了“星星使用”
- 用户无法按真实原因筛选
- “近三个月”对明细页价值偏低，但占用了显著交互空间

#### 2. 当前月度汇总文案会误导用户

`services/star-service/star-records.js` 与页面本地 fallback 当前都按如下方式生成月汇总：

- 当月净变化 `>= 0`：`本月共获得 X 颗星星`
- 当月净变化 `< 0`：`本月共使用 Y 颗星星`

问题在于：

- 它只说单边，不说净变化
- 它不区分“兑换使用”“过期失效”“未完成扣除”
- 用户会自然追问“这里的获得有没有扣掉过期和扣星”

#### 3. 当前记录行展示噪音偏大，但解释力不足

当前页面对每条记录都会展示：

- 标题
- 时间
- 点数
- `余额 XX 星星`

但对用户真正重要的信息反而没有正式表达：

- 这条减少是兑换、过期还是扣星
- 这条获得是永久有效，还是周末/月末到期
- 这条减少与任务未完成有没有关系

#### 4. 现有记录层已经具备区分大部分真实场景的事实字段

真实代码复核后确认，当前记录里已经有足够多的字段可供本期做语义归类：

- 任务获得记录：`type = income`，通常带 `source = task_complete`，并带 `expiryType / expiryDate`
- 奖励兑换记录：`type = expense`，但真实来源可能是 `reward_${rewardId}`、`reward_exchange` 或保护兑换相关变体
- 过期失效记录：`type = expense`，`sourceId = expired_${expiryType}`，来源为系统结算
- 必做任务扣星：`type = expense`，`source = task_penalty` 或任务扣星链路，且可能带 `originalTaskDate`
- 低频退回/撤销记录：例如 `reward_exchange_refund`、`task_makeup_refund`、`task_reset`、`task_makeup_refund_revoke`

因此本期不需要先改存储 schema，也不需要补录历史数据，主要问题在于展示层没有把这些事实翻译成用户能读懂的语义。

#### 5. 当前项目里已经存在“补打卡窗口”工具，但本期不重做规则

仓库里已有 `utils/task-backfill-window.js`，能够解释 `week / month / quarter / permanent` 对应的历史补打卡窗口。  
但 `M21J` 本期只改奖池页的展示与解释口径，不去顺手重做任务补打卡规则，也不在本期推进更大范围的星星结算语义重构。

本期要处理的是：

- “这次获得的星星什么时候失效”
- “为什么这里减少了”

而不是：

- “这条历史任务是否还允许补打卡”

### 功能范围

**包含**：
- ✅ 保留正式名称“星星记录”，但把页面语义从账务流水收敛为用户可读记录
- ✅ 重构一级类型筛选为高频路径：全部 / 任务获得 / 兑换使用 / 星星减少
- ✅ 重构时间筛选，移除低价值的近三个月明细窗口
- ✅ 重写月度汇总为“获得 / 减少 / 净结果”组合表达
- ✅ 在任务获得记录中展示 `expiryType / expiryDate` 对应的时效信息
- ✅ 降低逐条“余额”信息的视觉权重，突出变动原因和时效解释
- ✅ 在列表项中保留过期失效 / 未完成扣除 / 其他变动等语义标签，但不把低频类型抬到一级筛选
- ✅ 明确视觉基线，要求与奖池页卡片、色彩、圆角、阴影、交互密度保持一致
- ✅ 为缺失 `expiryType / expiryDate` 的旧记录提供兼容降级展示
- ✅ 补齐页面与纯函数测试

**不包含**：
- ❌ 修改星星获得、消费、过期结算的业务规则
- ❌ 修改 `task-backfill-window` 的补打卡资格语义
- ❌ 改动后端接口或新增云端 schema
- ❌ 回填历史老记录的缺失字段
- ❌ 重做整个奖池页或奖励兑换主链路

### 优先级

- **优先级**：P1
- **理由**：这不是结算正确性事故，但它已经直接影响用户对奖池页的理解和信任，属于高频体验层问题，且改造范围相对收敛，ROI 高。

## 技术方案

### 方案概述

`M21J` 采用“保留底层账务事实，新增一层用户语义翻译”的方案。核心思路不是推翻 `StarRecord` 或重做 `StarService`，而是在现有字段之上增加一层稳定的展示语义：

1. 先把原始记录归一化为页面可读的 `semanticType / title / subtitle / tag / amount / timingMeta`
2. 再基于归一化结果做一级筛选、摘要、列表标签和月份分组
3. 页面只消费归一化后的结构，不再直接把 `income / expense` 这种系统字段暴露给用户

这样可以在不动结算主链的前提下，把页面体验从“会计流水”提升到“用户能读懂的星星记录”，同时避免做出一套和奖池页脱节的新视觉语言。

### 关键设计决策

#### 决策1：正式名称保持“星星记录”，但语义不再是“收入/支出流水”

页面的正式名称继续使用“星星记录”，与奖池入口按钮保持一致。  
但页面的解释口径改为“最近发生了哪些星星变化”，而不是“收入/支出账目”。

用户关心的是：

- 我是通过什么得到的
- 我为什么失去了
- 这次获得会不会过期

因此筛选、摘要和列表标签都要围绕“变动原因”组织，而不是围绕“正数/负数”组织。

#### 决策2：一级类型筛选收敛为 4 个高频入口，详细原因用标签表达

一级类型筛选重构为：

- `all`：全部变动
- `task_income`：任务获得
- `reward_exchange`：兑换使用
- `loss_event`：星星减少

列表内的详细语义仍保留以下标签：

- `task_income`：任务获得
- `reward_exchange`：兑换使用
- `expired`：过期失效
- `task_penalty`：未完成扣除
- `other_change`：退回 / 撤销 / 其他低频变动

一级筛选与详细语义的关系如下：

- `task_income` 筛选：只看任务获得
- `reward_exchange` 筛选：只看兑换使用
- `loss_event` 筛选：看全部实际负向变动，至少包括 `reward_exchange / expired / task_penalty / 负向 other_change`
- `all`：展示全部记录，并通过标签区分 `expired / task_penalty / other_change`

详细归类规则采用已有记录事实字段推导，并按以下优先级执行：

- 负数且 `sourceId` 形如 `expired_*` 或系统过期来源 → `expired`
- 负数且任务惩罚来源或存在 `originalTaskDate` → `task_penalty`
- 负数且奖励兑换来源或保护兑换变体 → `reward_exchange`
- 正数且任务来源 → `task_income`
- 退款、退星、撤销完成、撤销补做退星、手动调整等其余记录 → `other_change`

说明：

- `reward_exchange` 识别不能只依赖单个 `source` 常量，必须兼容 `exchange / partial_protected_exchange / protected_exchange` 对应的消费记录，以及 `reward_${rewardId}` 这类真实来源格式。
- `other_change` 是低频兜底类，不是独立一级筛选项；它应主要通过列表标签可见，其中负向记录可被 `loss_event` 聚合命中，但不单独占用主筛选位。
- `loss_event` 作为一级筛选服务“我为什么少了星星”这个高频问题，因此它是按方向聚合的总入口；`reward_exchange` 则保留为高频专项快捷入口，两者允许存在包含关系。
- `loss_event` 至少要覆盖 `expired / task_penalty / task_reset / task_makeup_refund_revoke` 等真实负向记录，不能只收窄到过期和扣除两类。
- 为避免“主动兑换”和“被动损失”混在一起导致误解，`loss_event` 的摘要必须强制带构成拆分，至少显式列出 `兑换使用 / 过期失效 / 未完成扣除`。

这样既能覆盖当前高频路径，又不会因为低频类型过多把主筛选做重；同时也为现有代码里已存在的退款/撤销类记录保留正式落点。

#### 决策3：时间筛选收敛为“最近7天 / 本月 / 全部”

时间筛选重构为：

- `last7days`：最近7天，按今天向前滚动 7 天，不是自然周
- `currentMonth`：本月，指当前自然月，不是滚动 30 天
- `all`：全部

不再保留 `近三个月`，也不再把 `近一个月` 作为滚动 30 天窗口。原因：

- 明细页里长期明细价值低，老数据更适合看按月分组后的汇总
- “本月”比“近 30 天”更符合用户在奖池场景下的自然心智
- 保留 `全部` 后，老月份仍可通过月分组查看，不会丢信息

默认进入页时，时间范围默认选中 `currentMonth`，即先看“当前自然月”的最新明细，而不是默认看全部历史。

当月初 `currentMonth` 数据很少甚至为空时，不自动切换范围，避免页面“自己跳视图”；改为明确空态提示：

- 主文案：`本月还没有星星变化`
- 次文案：`可以看看最近7天，或查看全部记录`
- 操作：提供 `最近7天` 和 `全部` 的快捷切换

#### 决策4：时间范围与展示组织拆开，不混用

本期正式把“用户在看多大时间范围”和“页面怎么组织内容”拆成两层：

- 时间范围负责决定“当前看哪些数据”
- 展示组织负责决定“这些数据如何摘要、是否按月分块”

具体规则：

- `last7days`
  - 看最近 7 天滚动窗口的数据
  - 页面顶部使用“最近7天摘要”，例如 `最近7天获得 8 · 减少 3`
  - 列表直接按时间倒序展示，不再强调“本月”或按月标题
- `currentMonth`
  - 看当前自然月的数据
  - 页面顶部使用“本月摘要”，例如 `本月获得 20 · 减少 15`
  - 列表只展示当前月明细，不需要再拆多个“月份块”
- `all`
  - 看全部历史数据
  - 页面顶部只保留“总星数卡片 + 时间筛选 + 类型筛选”
  - 页面顶部不额外渲染“全部历史摘要卡”或弱化版总摘要
  - 列表按自然月分组，每个月块内再展示对应月份摘要

这样可以避免两类典型混乱：

- 用户切到 `最近7天`，却看到“本月任务获得 20”
- 用户切到 `本月`，结果页面还像在浏览多个月的月报

#### 决策5：区间摘要与月度摘要都改为“获得 / 减少”为主，“净结果”为辅

摘要区按当前时间范围输出，不再默认把所有摘要都写成“月份标题”：

- 在 `last7days` 下：
  - `all`：`最近7天获得 8 · 减少 3`
  - `task_income`：`最近7天任务获得 8`
  - `reward_exchange`：`最近7天兑换使用 2`
  - `loss_event`：`最近7天共减少 3`
  - `loss_event` 次文案：`兑换使用 2 · 过期失效 1 · 未完成扣除 0`
- 在 `currentMonth` 下：
  - `all`：`本月获得 20 · 减少 15`
  - 次文案：`兑换使用 8 · 过期失效 4 · 未完成扣除 3 · 其他变动 +2 · 余额净增 +7`
  - 单一类型筛选：
    - `task_income`：`本月任务获得 20`
    - `reward_exchange`：`本月兑换使用 8`
    - `loss_event`：`本月共减少 15`
    - `loss_event` 次文案：`兑换使用 8 · 过期失效 4 · 未完成扣除 3`
- 在 `all` 下：
  - 页面级不显示额外的“全部历史摘要”
  - 每个自然月分组块内再输出该月摘要：
    - `all`：`获得 20 · 减少 15`
    - 次文案：`兑换使用 8 · 过期失效 4 · 未完成扣除 3 · 其他变动 +2 · 余额净增 +7`
    - 单一类型筛选：`2026年4月任务获得 20`、`2026年4月兑换使用 8`、`2026年4月共减少 15`

规则：

- “任务获得”只统计 `task_income`
- “兑换使用”只统计 `reward_exchange`
- “过期失效”只统计 `expired`
- “未完成扣除”只统计 `task_penalty`
- “其他变动”统计 `other_change`，其值可正可负
- “减少” = 全部真实负向变动，至少包含 `reward_exchange + expired + task_penalty + 负向 other_change`
- “余额净增 / 净减” = `任务获得 - 减少 + 其他变动净值`
- 摘要文案必须同时跟随“时间范围 + 类型筛选”切换
- 只有 `all` 视图才按自然月分组；`last7days` 与 `currentMonth` 不再额外叠加多个月份块
- 详细原因拆分主要在 `all` 与 `loss_event` 的摘要次文案，以及记录标签中体现，不再全部抬成一级筛选

这样用户一眼就能看到：

- 当前查看区间内一共获得了多少
- 当前查看区间内又因什么减少
- 当前查看区间的最终净结果是净增还是净减

这样可以避免把“净变化”误当成“本月表现”，尤其能兼容“任务按周循环、星星按周末失效”的高频用户场景。不再出现“明明看最近7天，却继续显示本月标题”或“明明只看当前月，却还要读多个月块”的口径冲突。

#### 决策6：视觉基线必须复用奖池页，不再沿用旧时间线装饰语言

本期不允许把“星星记录”做成一套和奖池页脱节的新视觉系统。正式视觉基线如下：

- 页面底色沿用奖池页的浅灰底 + 白卡体系
- 摘要区、筛选区、列表区统一使用白卡、16rpx 左右圆角、克制阴影
- 主强调色沿用奖池页蓝色系，不新增新的主色体系
- 不再使用旧版 `star-records` 的时间线、渐变月份标题、左侧粗色条、强装饰圆点作为主视觉骨架
- 记录语义差异优先通过小标签、字重、次级说明表达，而不是大面积彩色块
- 筛选器应复用奖池页当前 tab/chip 的克制交互风格，不做额外夸张动画或重阴影
- 不保留旧页里偏装饰化的 `⭐` emoji 作为主图标，统一改用文字、金额和标签表达

这条约束的目标是：

- 与奖池页保持主题一致
- 保持简洁、精致、易懂
- 避免“功能上更清楚，但视觉上像另一个页面”

#### 决策7：任务获得记录必须直接展示时效信息

对于 `task_income` 记录：

- `expiryType = permanent` → 展示 `永久有效`
- `expiryType = week / month / quarter` 且存在 `expiryDate` → 展示 `周末到期 / 月末到期 / 季末到期` + `YYYY-MM-DD 到期`
- 若旧记录缺失字段 → 不展示错误文案，只降级为不显示时效副文案

注意：

- 本期展示的是“这次获得的星星何时失效”
- 不是“任务补打卡资格是否截止”
- 页面文案不得直接把两者混为一谈
- 对惩罚类记录，继续保留“任务截止时间 + 扣星执行时间”的双时间语义，作为副文案或次级时间行展示

这样既回应了用户对“本周结束 / 本月结束”理解的真实需求，也避免页面提前绑定尚可能继续演进的任务层规则口径。

#### 决策8：逐条“余额 XX 星星”不再作为主信息

当前每行都展示“余额 XX 星星”，噪音高于价值。`M21J` 调整为：

- 页头统一展示当前可用星星总数
- 列表项默认不再突出逐条余额
- 若后续确认仍有价值，可在次级文案或展开态保留，但不作为主信息

本期默认方案是移除逐条余额展示，让列表重点回到“原因 + 时间 + 金额 + 时效”。

#### 决策9：旧记录兼容按“保守降级”处理

历史记录里可能存在：

- `source` 不是最新正式值
- `expiryType / expiryDate` 缺失
- 描述文案较旧

本期兼容策略：

- 归类优先依赖结构化字段，文案只作兜底
- 无法精确识别时归到 `all` 可见，但不误判到错误类别
- 无时效字段时不强行捏造“本周结束 / 本月结束”说明

- **输出**：`semanticType`
- **职责**：把原始账务事实翻译为用户语义分类，并兼容奖励兑换变体与退款/撤销类低频记录

- **输入**：归一化记录、当前一级筛选
- **输出**：`boolean`
- **职责**：运行时判断记录是否命中一级筛选；不再依赖单值 `primaryFilterType` 字段，其中 `loss_event` 需覆盖全部真实负向变动，`reward_exchange` 为其高频专项子集

- **输入**：原始 `StarRecord`

- **职责**：统一标题、副文案、标签、金额显示和列表标签语义，并保留惩罚记录的双时间展示

**函数4**：`buildMonthSummary(records, activeFilter)`
- **输入**：同月归一化记录列表
- **输出**：获得 / 减少 / 净结果组合文案，及按筛选口径切换的 scoped 文案
- **职责**：只在 `all` 视图下构建自然月分组摘要，并保证月份摘要与当前筛选一致

**函数5**：`buildScopeSummary(records, activeTimeScope, activeFilter)`
- **输入**：当前时间范围下的归一化记录列表
- **输出**：区间级摘要文案
- **职责**：为 `last7days` / `currentMonth` 输出对应区间摘要，避免继续误用月度标题

## 替代方案

### 方案A：只改文案，不改筛选与汇总结构

- **做法**：保留 `收入 / 支出` 和 `近三个月`，只调整个别中文文案。
- **问题**：根因不在个别词句，而在信息架构；用户仍无法按真实场景筛选，也仍会被月汇总误导。
- **结论**：不采用。

### 方案B：直接做更大的星星域规则重构

- **做法**：把补打卡窗口、获得时效、过期结算和明细页一起重做。
- **问题**：范围过大，会把一个高 ROI 的页面澄清问题扩成跨任务域、星星域、消息域的综合治理。
- **结论**：不采用，本期只做明细页语义收口。

### 方案C：继续保留逐条余额，只增加分类标签

- **做法**：在现有布局上追加标签，不动整体层级。
- **问题**：页面噪音仍然偏高，月汇总和时间筛选问题依旧存在，收益不足。
- **结论**：不采用。
