## 需求分析

### 功能描述

`M21J` 第一版设计和实现，把“星星记录”页同时做成了两件事：

- 一方面，它想解释“我现在还有多少星星”
- 另一方面，它又想解释“最近发生了哪些星星变化”

验收反馈表明，这两个问题混在同一页里会直接造成理解冲突：

1. 奖池页顶部已经展示当前星星余额，进入“星星记录”后再看一遍余额，会让用户觉得重复、占位且没有新增信息。
2. 星星记录页筛选器下方的区间汇总，描述的是“最近7天/本月内发生了多少获得与减少”，它是时间窗口内的流量，不是当前余额；当这块数字与当前余额对不上时，用户会直接怀疑系统算错了。
3. 用户真正关心的其实是两个完全不同的问题：
   - `现在还剩多少，可用星星由哪些有效期桶组成，哪些快过期`
   - `最近为什么涨了/减了，具体是哪条记录造成的`

因此，本轮修订不再把“记录页做成总账解释页”，而是把职责正式拆开：

- 奖池页负责解释“当前可用余额”
- 星星记录页负责展示“历史变动明细”

### 业务价值

- [x] 用户价值：把“当前余额解释”和“历史变动查看”分离，避免同页两套口径打架。
- [x] 产品价值：奖池页更像余额主页，星星记录页更像明细页，信息架构更符合用户心智。
- [x] 技术价值：避免继续在记录页堆叠摘要逻辑，把余额解释建立在真实可用星星分组之上，而不是建立在时间窗口汇总之上。

### 事实基线（2026-04-15，基于当前代码与验收反馈）

#### 1. 奖池页已经具备“当前余额”入口

`pages/rewards/rewards.js` / `pages/rewards/rewards.wxml` 当前已展示：

- `totalPoints / formattedPoints`
- `expiringPoints / expiryDate`
- “星星记录”入口按钮

也就是说，奖池页天然就是“当前余额”的入口页，不需要在进入明细后再重复一张大余额卡。

#### 2. 星星记录页当前把“余额”和“周期流量”混在了一起

`packageMessage/pages/star-records/star-records.js` 当前仍持有：

- `totalStars`
- `scopeSummary`

这两个信息的口径并不一致：

- `totalStars` 表示当前可用余额
- `scopeSummary` 表示当前筛选时间范围内的区间变动

两者在业务上本来就可能对不上，因此同屏强展示会制造认知冲突。

#### 3. “把整个流水页按有效期分组”不是可靠方案

从真实代码看，收入记录通常带 `expiryType / expiryDate`，但很多通用支出记录不会稳定记录“到底消耗了哪一类有效期星星”：

- 通用扣星走 `consumeStarsByExpiryOrder(...)`，实际按先到期优先扣减
- 但保存流水时，很多情况下只落一条通用支出记录，不总是带具体 `expiryType`
- 只有特定类型扣减链路才会显式写入 `expiryType`

这意味着：

- “当前可用余额的有效期构成”是真实可解释的，因为它来自当前 `StarGroup`
- “历史流水逐条归属到哪个有效期桶”并不总是有完整事实支撑

所以，不能把星星记录页主视图改成“按有效期分桶的总账流水”，否则会制造“看起来精确、但实际并不完全真实”的误导。

#### 4. 当前可用星星的有效期构成是可真实计算的

`StarService` 当前已经能读取非空星星分组，并且分组天然带有效期语义。  
这正是解释“当前余额由哪些桶构成”的正确事实来源。

因此，本期应把“有效期解释”前移到奖池页，而不是继续压在记录页。

#### 5. 奖池页现有余额口径已经绑定有效孩子视角，新构成模块必须完全复用

真实代码复核后确认，奖池页当前的核心余额数据都不是“全用户总和”，而是绑定到当前有效孩子视角：

- `totalPoints` 通过 `effectiveChildId` 调用 `starService.getTotalStars(effectiveChildId)`
- `expiringPoints` 通过同一 `effectiveChildId` 调用 `starService.getExpiringStarsInfo(effectiveChildId)`

因此本期新增的“当前可用星星构成”也必须使用完全相同的 scope：

- 同样基于 `effectiveChildId`
- 同样只解释当前奖池正在服务的那个孩子

不能出现：

- 顶部总星星是当前孩子
- 但构成分桶是全家庭总和

否则页面会立刻出现新的“数字对不上”问题。

#### 6. 仅复用 `effectiveChildId` 还不够，奖池页三块数据必须共享同一份“当前可用星星快照”

继续深入复核真实代码后确认，当前奖池页三类相关数据并不天然来自同一条计算链：

- `totalPoints` 走 `starService.getTotalStars(effectiveChildId)`，底层当前是直接汇总分组星星数
- “当前可用星星构成”准备基于 `getStarGroups(effectiveChildId)` 做有效期分桶
- `expiringPoints` 走 `getExpiringStarsInfo(effectiveChildId)`，这里已经显式过滤了 `!group.isExpired()`

问题是：

- `getTotalStars()` 当前实现并未明确排除已过期分组
- `getStarGroups()` 当前实现也只是取“非空分组”，并未明确排除已过期分组
- 只有即将过期信息在显式按“未过期且在提醒窗口内”计算

这意味着如果本期只是“各自复用同一个 `effectiveChildId`”，但仍分别走三套底层计算口径，奖池页仍然可能出现：

- 顶部总星星 = A
- 构成分桶求和 = B
- 即将过期提示 = C

三者彼此有 scope 一致，但事实口径不一致，用户仍会认为系统算错。

因此本期必须新增一个统一的“当前可用星星快照”权威口径，至少同时产出：

- `totalStars`
- `buckets`
- `expiringInfo`

并保证这三者都来自同一批“当前有效、未过期、属于当前 effectiveChildId 的分组”。

### 功能范围

**包含**：
- ✅ 奖池页新增“当前可用星星构成”信息块，解释余额由哪些有效期桶组成
- ✅ 奖池页保留并强化快过期提示，明确“系统优先使用更早到期的星星”

## 技术方案

### 方案概述

本轮修订采用“按问题拆页”的方案，而不是继续在记录页叠加解释信息：

1. 奖池页只回答“现在还剩多少、哪些快过期、余额由哪些桶组成”
2. 星星记录页只回答“最近发生了什么变化”
3. 奖池页顶部总星星、余额构成、即将过期提示必须共享同一份“当前可用星星快照”权威口径
4. 有效期解释基于当前 `StarGroup` 聚合结果，不基于历史流水倒推
5. 历史流水继续基于 `StarRecord` 做语义归类、筛选和分组，但不再承担余额解释职责

### 关键设计决策

#### 决策1：奖池页成为唯一的余额解释入口

奖池页保留顶部“我的星星”大卡，作为唯一的余额总览入口。  
进入“星星记录”后，不再重复展示总余额。

新增一块“当前可用星星构成”信息区，按有效期桶展示当前余额：

- `本周到期`
- `本月到期`
- `本季度到期`
- `永久有效`

展示规则：

- 只展示值大于 0 的桶
- 按到期优先级排序：`week → month → quarter → permanent`
- 底部固定说明：`系统会优先使用更早到期的星星`
- 若存在即将到期星星，优先高亮最早到期桶，并复用现有最早到期提示
- 取数 scope 必须与奖池页现有 `effectiveChildId` 完全一致
- 顶部总星星、余额构成、即将过期提示必须统一来自同一份“当前可用星星快照”，不能分别走三套独立计算

这样用户在奖池页就能回答：

- 我现在有多少星星
- 这些星星怎么构成
- 哪些应该优先用掉

#### 决策2：星星记录页只做“历史变动明细”

星星记录页正式退回为“明细页”，不再承担余额解释职责：

- 去掉顶部余额大卡
- 去掉筛选器下方的周期汇总卡
- 不再展示“本月获得多少 / 减少多少 / 余额净增多少”这类概括性面板

页面只保留：

- 页面标题
- 时间筛选
- 类型筛选
- 记录列表
- 空态引导

同时明确退役以下旧数据链：

- `data.totalStars`
- `loadStarRecords()` 中对 `starService.getTotalStars()` 的调用
- 任何仅为顶部余额卡服务的 `setData` 字段与测试断言

这样用户进入该页后，预期会稳定收敛为：

- 看最近变化
- 查某条记录为什么增加/减少
- 回溯历史月份

而不会再把它误认为“当前余额解释页”。

#### 决策3：不采用“按有效期分组整张流水页”

这是本轮最重要的排除决策。

不采用的原因不是体验想法不好，而是事实基础不够稳定：

- 当前余额确实有明确的有效期分组事实
- 但历史支出流水并不总能精确绑定到具体有效期桶

因此：

- 奖池页按有效期解释余额：可行且真实
- 星星记录页按有效期重组整个流水：不采用

记录页仍按“事件语义”组织，而不是按“余额桶”组织。

#### 决策4：记录页保留 4 个高频类型筛选

一级类型筛选保留为：

- `all`：全部
- `task_income`：任务获得
- `reward_exchange`：兑换使用
- `loss_event`：星星减少

列表详细标签仍保留：

- `任务获得`
- `兑换使用`
- `过期失效`
- `未完成扣除`
- `其他变动`

说明：

- `loss_event` 继续覆盖全部真实负向变动
- `reward_exchange` 保留单独入口，因为“兑换使用”是高频主动操作
- 低频类型继续通过标签表达，不再占用一级筛选位

#### 决策5：记录页默认看“最近7天”

既然页面职责已经收敛为“历史变动明细”，默认时间范围就应落在最有现实意义的查看窗口：

- 默认时间：`最近7天`
- 备选时间：`本月 / 全部`

原因：

- 用户点进明细页，最常见诉求是看最近发生了什么
- `最近7天` 比 `本月` 更像“活动流”
- 历史仍可以通过 `本月` 和 `全部` 查看

空态规则：

- `最近7天` 无记录：提示切到 `本月` 或 `全部`
- `本月` 无记录：提示切到 `最近7天` 或 `全部`
- 全历史无记录：提示去完成任务

#### 决策6：`全部` 视图只按月分组，不再做月度金额汇总

`all` 视图下仍按自然月分组，方便浏览历史。  
但每个月份块只保留：

- 月份标题
- 该月记录列表

不再保留：

- `获得 20 · 减少 15`
- `本月净增 +7`
- `兑换使用 8 · 过期失效 4 ...`

原因：

- 月度汇总会再次把页面拉回“会计报表”心智
- 用户在明细页里更关心“这个月发生了什么”，不是“这个月结了什么账”

#### 决策7：获得记录继续直接展示时效信息

对于 `task_income` 记录，继续保留时效副文案：

- `permanent` → `永久有效`
- `week` → `本周结束失效 · YYYY-MM-DD`
- `month` → `本月结束失效 · YYYY-MM-DD`
- `quarter` → `本季度结束失效 · YYYY-MM-DD`
- 缺字段旧记录 → 保守降级，不强造文案

惩罚记录继续保留双时间语义：

- `应该完成：YYYY-MM-DD`
- `实际扣星：YYYY-MM-DD HH:mm`

#### 决策8：视觉基线统一向奖池页靠拢，但两页层级不同

视觉方向保持一致：

- 浅灰页面背景
- 白卡体系
- 蓝色系强调
- 克制阴影与圆角

但信息层级要明确区分：

- 奖池页：强调“当前余额 + 构成 + 快过期提醒”
- 星星记录页：强调“筛选 + 明细列表”

记录页不再保留任何看起来像“总览面板”的大信息块。

### 核心函数

**函数1**：`buildAvailableStarSnapshot(groups, userId)`
- **输入**：当前用户相关的原始星星分组、`userId`
- **输出**：统一的奖池页快照结构
- **职责**：先过滤出“当前有效、未过期、属于当前用户”的分组，再一次性产出 `totalStars / buckets / expiringInfo`

**函数2**：`buildAvailableStarComposition(validGroups)`
- **输入**：已过滤后的有效分组
- **输出**：奖池页可直接渲染的余额构成结构
- **职责**：把真实可用余额解释成“本周到期 / 本月到期 / 本季度到期 / 永久有效”几个桶

**函数3**：`classifyStarRecord(record)`
- **输入**：原始 `StarRecord`
- **输出**：`semanticType`
- **职责**：把流水归类为任务获得、兑换使用、过期失效、未完成扣除或其他变动

**函数4**：`buildDisplayRecord(record)`
- **输入**：原始 `StarRecord`
- **输出**：记录页可直接渲染的展示结构
- **职责**：统一标题、时效副文案、标签和双时间显示

**函数5**：`buildStarRecordViewModel(records, options)`
- **输入**：原始记录、当前筛选条件
- **输出**：记录页视图模型
- **职责**：只负责筛选和分组，不再携带周期汇总卡数据

10. 检查任务获得记录，确认仍能看到星星何时失效。

## 替代方案

### 方案A：维持当前实现，只微调文案

- **做法**：保留记录页顶部余额卡和周期汇总卡，只改中文文案。
- **问题**：根因不是措辞，而是把“余额解释”和“历史流水”混在一起。
- **结论**：不采用。

### 方案B：把星星记录页重做成按有效期分桶的流水总账

- **做法**：让整张记录页按 `本周到期 / 本月到期 / 永久有效` 等桶展示所有历史流水。
- **问题**：当前很多历史支出记录并不具备精确的有效期归属事实，强行分桶会误导用户。
- **结论**：不采用。

### 方案C：奖池页解释余额，记录页只看历史变动

- **做法**：奖池页承接余额构成与快过期提示；记录页回归明细页。
- **优点**：与真实数据结构一致，也与用户心智一致。
- **结论**：采用。

### 方案D：继续保留逐条余额，只增加分类标签

- **做法**：在现有布局上追加标签，不动整体层级。
- **问题**：页面噪音仍然偏高，月汇总和时间筛选问题依旧存在，收益不足。
- **结论**：不采用。
