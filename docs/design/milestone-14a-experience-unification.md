## 需求分析

### 功能描述

M12 已完成首页结构拆分，M13 已完成质量闸门升级，当前项目进入体验层治理阶段。结合现状代码，首页与奖池页在“任务是主路径、奖励是辅助反馈”这一核心体验上仍不一致：首页把奖励进度卡放在任务列表前，并在未配置真实奖励时直接阻断任务完成；奖池页在“奖励已清空 / 只有示例奖励”场景下又缺少明确空态表达，导致用户对“能不能先做任务、奖励现在是什么状态、谁可以去配置奖励”这三件事产生混淆。

M14A 的目标不是重做业务规则，也不是引入新的技术框架，而是在现有微信小程序原生架构下，统一首页与奖池页的主次关系、空态语义和角色表达，让任务主路径更顺滑，让奖励区承担明确、稳定、可理解的辅助反馈职责。

### 业务价值

- [x] 用户价值：避免“没有配置奖励就不能完成任务”的割裂体验，让孩子先完成任务、先积累星星，再理解奖励状态。
- [x] 技术价值：在不改动服务层契约和存储结构的前提下，统一首页与奖池页的展示语义，降低后续体验迭代的维护成本。
- [x] 业务价值：为 M14B 的文档统一和后续视觉/文案精修建立稳定的交互基线。

### 事实基线（2026-03-26，设计前）

#### 1. 首页当前会因“未配置真实奖励”阻断任务完成

`pages/index/modules/index-task-actions.js` 中的 `ensureRewardSetupForCompletion(page)` 会在以下场景直接阻止任务完成：

- `calculateNextAvailableReward()` 返回默认占位奖励
- 奖励列表为空
- 或奖励列表只包含示例奖励

命中后当前逻辑会：

1. 清理 `processingTaskId`
2. 给 `nextReward.showSetupTip = true`
3. 弹出“需要设置奖励”模态框
4. 返回 `false`

这意味着“是否配置奖励”当前是任务完成前置条件，与用户已确认的产品方向不一致。

#### 2. 首页奖励区域已经具备部分提示状态，但仍以阻断逻辑为中心

`pages/index/modules/index-reward-flow.js` 已能识别：

- `hasNoRealReward`
- `hasOnlyExampleRewards`
- `nextReward.showSetupTip`

并在首页奖励卡内展示“还没有设置奖励哦”的提示文案。但当前这套状态与任务完成逻辑没有被统一使用，导致页面一边显示提示、一边在点击完成任务时强制拦截。

#### 3. 首页信息层级仍偏向“奖励在前，任务在后”

`pages/index/index.wxml` 当前结构中：

1. 顶部栏
2. 任务进度圆环
3. 搜索区
4. 奖励进度卡
5. 今日任务列表

奖励卡位于任务列表之前，视觉上容易把“奖品进度”误读为首页主操作区，与本项目“任务打卡是核心主路径”的产品定位不一致。

#### 4. 奖池页对“已清空奖励”场景缺少明确空态

`pages/rewards/rewards.js` 中，当 `allRewards.length === 0 && hasCustomRewards` 时，页面会写入：

- `rewards: []`
- `availableRewards: []`
- `claimedRewards: []`
- `nextReward: null`

然后直接返回。当前 `pages/rewards/rewards.wxml` 没有与之对应的显式空态卡片，因此页面会落入“没有奖励网格，但仍保留奖励页框架”的模糊状态，用户很难判断这是“未配置奖励”“奖励被清空”“还是加载失败”。

#### 5. 家长和孩子在“奖励未配置”场景下需要不同动作，但当前表达不够清晰

产品真实需求已经明确：

- 家长拥有创建和管理奖励的权限
- 孩子只负责查看奖励、积累星星、打卡和重置任务
- 不存在“家长代孩子创建任务”的补充需求

因此在奖励未配置时：

- 家长视角应该获得明确的配置入口或引导动作
- 孩子视角应该只看到解释性提示，而不是被引导去执行其无权限的配置动作

### 功能范围

**包含**：

- ✅ 首页改为“任务优先、奖励辅助”的信息层级
- ✅ 首页任务完成不再因未配置真实奖励而被阻断
- ✅ 首页奖励区在“未配置真实奖励 / 只有示例奖励”时降级为轻提示，而不是主流程门槛
- ✅ 奖池页增加明确的奖励空态卡，并区分家长视角与孩子视角
- ✅ 统一“无真实奖励”的判定语义，包括奖励为空、仅示例奖励、曾配置后被清空三类场景
- ✅ 示例奖励完全退出正式奖励体验：不进入奖励墙、不参与首页正式奖励摘要、不参与正式进度表达
- ✅ 在现有 WXML/WXSS/页面脚本内完成体验与视觉统一，不引入新技术栈

**不包含**：

- ❌ 不修改奖励、星星、任务的服务层业务规则
- ❌ 不修改云同步、存储结构、API 契约和双环境切换机制
- ❌ 不在 M14A 内补写 API 文档和测试总览文档，这部分归 M14B
- ❌ 不做全站视觉重设计，只聚焦首页与奖池页主路径
- ❌ 不改变家长/孩子原有权限边界

### 优先级

- **优先级**：P1
- **理由**：该问题不会像 M11 那样直接造成数据错误，但它持续影响主路径流畅度和页面理解成本，已经成为当前产品体验上的主要短板。

## 技术方案

### 方案概述

M14A 采用“中等幅度重排，不改底层契约”的方案。具体做法是：

1. 首页调整为任务优先，把任务列表提升为主内容区，奖励卡降为辅助反馈区。
2. 移除首页完成任务前的“必须先配置奖励”拦截逻辑，让任务完成和星星累计继续按现有服务层主链路执行。
3. 奖励未配置时，首页只展示轻提示；奖池页则承担主解释和主引导职责。
4. 奖池页对家长和孩子展示不同空态表达：家长可看到去配置奖励的动作入口，孩子只看到解释性文案。

这样做的核心是统一页面语义：

- 首页回答“今天要做什么、我做完会得到什么反馈”
- 奖池页回答“奖励现在是什么状态、我还差多少、如果没配置接下来该谁处理”

兼容性约束：

- M14A 不引入新的 npm 依赖、UI 框架或构建工具
- 仅基于现有微信小程序原生 `WXML / WXSS / JS` 与既有服务层接口增量实现
- 不改变当前双环境切换方式和 API 配置位置

### 技术选型

| 技术点 | 选择方案 | 替代方案 | 选择理由 |
|--------|---------|---------|---------|
| 页面改造方式 | 基于现有 `index.wxml` / `rewards.wxml` 和对应样式增量调整 | 引入新组件体系或重写整页 | 当前页面已完成 M12 结构治理，继续增量修改成本最低、兼容性最好 |
| 奖励未配置判定 | 复用现有 `nextReward.isDefault`、`showSetupTip`、`visibleRewards.isExample` 及奖池页 `isExampleReward()` 识别能力 | 新增服务层“是否已配置奖励”专用接口 | 当前前端已有足够状态基础，服务层无必要扩口 |
| 完成任务行为 | 取消完成前置拦截，让成功后继续刷新奖励区 | 保留阻断，只优化文案 | 用户已明确希望任务完成仍然成功，阻断方案不再成立 |
| 角色差异表达 | 基于登录用户奖励管理权限区分 CTA，并兼容当前只读孩子视角限制 | 在服务层注入角色型视图模型 | 这是纯表现层差异，不应下沉到服务层，且必须贴合现有 `isReadonlyView` / 权限语义 |
| 共享状态抽象 | 优先在页面模块内收敛体验状态，必要时只抽一个轻量纯函数 helper | 在 M14A 内进一步做结构治理 | M14A 重点是体验统一，不再扩大为结构重构 |

### 数据模型

M14A 不新增业务数据模型，只新增页面层体验状态概念。实现时可采用页面内部字段，不要求建立独立类。

```typescript
interface RewardExperienceState {
  hasRealRewards: boolean;
  hasOnlyExampleRewards: boolean;
  hasClearedRewards: boolean;
  shouldShowSetupHint: boolean;
  canManageRewards: boolean;
  viewMode: 'parent-manage' | 'child-readonly';
  homeHintMode: 'normal' | 'setup';
  rewardPageEmptyMode: 'none' | 'parent-setup' | 'child-explain';
}
```

说明：

- `hasRealRewards`：存在可被视为真实奖池内容的奖励
- `hasOnlyExampleRewards`：当前只有示例奖励，应按“未完成真实配置”处理
- `hasClearedRewards`：历史上存在过自定义奖励标记，但当前奖励为空
- `shouldShowSetupHint`：首页是否需要展示轻提示
- `canManageRewards`：是否拥有奖励管理权限，优先按登录用户权限判断，而不是按当前孩子积分归属判断
- `viewMode`：体验视角只分为“可管理”与“只读解释”，避免把实现错误地简化成当前积分所属用户角色
- `rewardPageEmptyMode`：奖池页空态展示策略

### 接口设计

M14A 不新增后端或服务层接口，仅定义前端内部实现边界。

**页面内部建议函数**：

| 方法 | 说明 | 参数 | 返回值 |
|------|------|------|--------|
| `buildHomeRewardState()` | 统一首页奖励摘要与提示态判定 | `({ nextReward, visibleRewards, canManageRewards })` | `{ shouldShowSetupHint, hintText, rewardSummaryMode }` |
| `buildRewardPageState()` | 统一奖池页空态与 CTA 判定 | `({ rewards, hasCustomRewards, canManageRewards })` | `{ emptyMode, ctaVisible, ctaText, ctaUrl }` |
| `completeTask()` 调整 | 去除奖励未配置前置阻断 | `({ taskId })` | 维持现有任务完成结果契约 |

判定约束：

1. 奖池页必须显式过滤示例奖励，过滤规则复用现有 `isExampleReward()` 能力或等价逻辑。
2. “无真实奖励”判定必须基于过滤示例奖励后的结果，不能把示例奖励当作正式奖励墙内容。
3. 家长 CTA 是否展示，以登录用户奖励管理权限为准；不能以当前积分所属孩子身份替代。
4. 首页 `isReadonlyView` 下的奖励快捷入口拦截策略不在 M14A 放开范围；孩子/只读视角的奖池空态通过底部 Tab 或直接进入奖池页承接。

## 视觉与状态规格

### 视觉目标

- 首页视觉目标：任务主区优先，奖励反馈存在但不抢首屏主操作权
- 奖池页视觉目标：奖励墙仍然是主视觉区，空态也应保留“奖池”而不是“系统空白”的感受
- 非回退约束：首页首屏必须仍能看到紧凑奖励摘要，不能把奖励反馈完全压出首屏
- 非回退约束：奖池页在有真实奖励时必须保持“可浏览、可收集、可对比”的奖励墙氛围，不能被大段说明文案挤压成说明页

### 首页奖励摘要卡规格

首页奖励区采用“轻量化卡片”而不是主视觉大卡，规格如下：

| 项目 | 规格 |
|------|------|
| 位置 | 位于任务区标题/日期导航之后、任务项列表之前，属于任务主区内的辅助摘要 |
| 外层 | 复用现有 `.card` 基础风格，可补最小 modifier |
| 内边距 | `20rpx` |
| 圆角 | 跟随现有卡片体系，默认不低于 `16rpx` |
| 阴影 | 不额外增加阴影，避免与任务主卡竞争 |
| 主标题字号 | `24rpx` |
| 辅助说明字号 | `22rpx-24rpx` |
| 信息密度 | 保留星星数、下一奖励摘要、轻提示三类关键信息，不再铺满整块视觉空间 |

### 奖池页空态卡规格

空态卡不是占位文字，而是替代奖励网格的正式内容块：

| 项目 | 规格 |
|------|------|
| 位置 | 奖励墙主区内，直接替代空奖励网格 |
| 结构 | 图标 + 标题 + 说明 + CTA（家长视角） |
| 视觉 | 保持奖励页的“收藏墙”语义，不做系统错误页样式 |
| 按钮 | 复用现有按钮风格，不额外设计新按钮体系 |
| 触摸目标 | CTA 点击区域不低于 `88rpx` 高 |

### 空态卡文案

家长视角空态：

```text
🎁
还没有设置奖励
先去配置第一个奖励吧，孩子完成任务后就能看到目标了
[去设置第一个奖励]
```

孩子视角空态：

```text
🎁
继续做任务积攒星星吧
奖励由家长设置，先把今天的任务完成也一样会积累星星
```

约束：

- 家长视角 CTA 复用 `/packageManage/pages/reward-manage/reward-manage`
- 孩子视角不出现可触发的配置动作
- 空态文案必须具体，不使用“暂无数据”“请稍后再试”这类系统化占位语

### 交互状态表

#### 首页奖励摘要

| 状态 | 触发条件 | 页面表现 |
|------|---------|---------|
| Loading | 首次加载奖励数据中 | 保持现有 loading 机制，不新增复杂骨架 |
| Success-正常 | 存在真实奖励 | 展示当前星星、下一奖励摘要、紧凑进度反馈 |
| Success-已达成 | 奖励刚达成或全部已领 | 展示达成反馈或“可继续积累”反馈 |
| Empty-未配置 | 无真实奖励 / 仅示例奖励 / 已清空奖励 | 展示轻提示，不阻断任务完成 |
| Error | 奖励加载失败 | 维持现有 toast 错误提示，不在首页新增重型错误卡 |

#### 奖池页主区

| 状态 | 触发条件 | 页面表现 |
|------|---------|---------|
| Loading | `loadRewardsData()` 执行中 | 保持现有 `wx.showLoading` 或转圈，M14A 不扩展骨架屏设计 |
| Success-正常 | 过滤示例奖励后仍有真实奖励 | 展示奖励墙、Tab 和奖励详情流 |
| Empty-家长 | 过滤示例奖励后无真实奖励，且登录用户可管理奖励 | 展示家长空态卡 + CTA |
| Empty-孩子 | 过滤示例奖励后无真实奖励，且登录用户无管理权限 | 展示孩子解释空态，无 CTA |
| Error | 数据加载失败 | 延续现有 Toast 失败提示，M14A 不新增独立错误卡或重试按钮 |

### 用户旅程目标

| 阶段 | 目标感受 | 设计落点 |
|------|---------|---------|
| 5秒 | 我知道这是做什么的 | 首页首屏先看到任务主区，同时仍能感知奖励存在 |
| 5分钟 | 我进步了 | 完成任务后立即获得星星与奖励摘要反馈，不再被配置状态打断 |
| 长期 | 这个系统值得信任 | 首页和奖池页对“未配置奖励”的解释一致，不出现忽而阻断、忽而空白的矛盾体验 |

## 替代方案

### 方案A：最小改动，只去掉阻断模态

做法：

- 仅修改 `index-task-actions.js`
- 不调整首页层级
- 不增加奖池页空态卡

优点：

- 改动最小，开发成本最低

缺点：

- 首页和奖池页语义仍不统一
- 用户仍可能在奖池页看到模糊空状态
- 无法解决“任务主路径优先级不清晰”的问题

不选原因：

只能修一个点，不能完成 M14A 的体验统一目标。

### 方案B：中等幅度重排，保持底层契约不变

做法：

- 首页改为任务优先、奖励辅助
- 取消完成任务前置阻断
- 奖池页新增显式空态和角色差异表达

优点：

- 改动范围聚焦在体验层
- 不影响服务层和双环境机制
- 能一次性解决主路径、空态和角色表达三类问题

缺点：

- 需要同时改 WXML、WXSS 和页面行为测试

选择原因：

这是当前性价比最高、与项目现状最匹配的方案。

### 方案C：直接做完整视觉翻新和跨页面组件化

做法：

- 同时重做首页、奖池页和共用卡片组件
- 大幅调整视觉语言和组件结构

优点：

- 理论上可获得最强的一致性

缺点：

- 超出 M14A 范围
- 风险和验证成本显著增加
- 容易再次演变成结构治理项目

不选原因：

当前项目刚完成 M12/M13，优先级应是体验统一而不是再次扩大重构范围。
