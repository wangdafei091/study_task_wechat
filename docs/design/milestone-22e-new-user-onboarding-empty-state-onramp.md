## 需求分析

### 功能描述

`M22A` 已完成治理与准入控制，`M22L` 已完成统一邀请码模型和“新用户直达家庭”主链路。当前系统已经具备“让用户进来”和“让用户加入家庭”的正式能力，但从真实使用视角看，首次进入后的体验仍然是割裂的：

1. 新用户虽然可以通过邀请码进入，但进入后下一步该做什么，依然要靠用户自己猜。
2. 家庭未建立、没有孩子成员、没有任务、没有奖励时，多个页面都在各自输出提示，但没有形成同一条最小可用路径。
3. 现有“首次启动”只会写入一条欢迎消息，不是正式的页面级 onboarding，也不能承接用户当前所处阶段。

`M22E` 的目标不是做一套重交互、重插画、重遮罩的新手教学，而是在现有微信小程序页面结构上，建立一套轻量、连续、低打扰的引导与空态体系，让新用户在首次进入和关键空状态下都能明确知道：

- 我现在处于哪一步
- 下一步最推荐做什么
- 做完之后会发生什么

### 业务价值

- [x] 用户价值：降低首次使用时的理解成本，减少“进入了，但不知道下一步做什么”的停滞。
- [x] 产品价值：把 `M22A / M22L` 已经打通的准入与邀请能力，真正转化为可用、可传播的用户体验。
- [x] 技术价值：将“首次进入 / 空态引导 / 最小可用路径”从分散文案提升为正式页面契约，为后续 `M22C` 的页面复杂度治理提供稳定目标。

### 功能范围

**包含**：

- [x] 梳理并正式化新用户首次进入后的最小可用路径
- [x] 收口 `access-gate`、`family-settings`、首页关键空态的文案、层级与 CTA
- [x] 为首次进入和关键空态建立统一的阶段判断模型
- [x] 设计“邀请进入后的一次性承接提示”与“首页阶段卡片”机制
- [x] 复用现有奖励页空态经验，统一空态设计原则
- [x] 补齐对应页面测试和引导阶段测试口径

**不包含**：

- [x] 不重做邀请码模型、发码治理和家庭加入后端事务，这些已在 `M22L` 完成
- [x] 不新增复杂的新手浮层、全屏 walkthrough、连续 coach mark 动画
- [x] 不进入 `task-edit` 复杂度治理，这属于 `M22C`
- [x] 不收口业务层直接存储访问与低价值残留，这属于 `M22F`
- [x] 不调整系统管理员、系统用户治理和邀请码中心的管理能力边界
- [x] 不重做首页奖励进度区、搜索面板、日期导航和表现记录区，只在既有信息架构中插入轻量引导卡

### 优先级

- **优先级**：P0
- **理由**：`M22A / M22L` 已完成“能进入、能加入、能发码”的能力底座，当前最直接影响真实使用转化的缺口，已经从能力缺失转变为体验缺失。

## 现状问题复盘

### 问题1：新用户已能进入系统，但下一步路径仍然分散

当前新用户可能从多个入口进入系统：

- `pages/access-gate/access-gate.js`
  - `manual_input`
  - `share_pending_login`
  - `confirm_join_family`
  - `no_action_needed`
- `packageManage/pages/family-settings/family-settings.js`
  - 当前虽命名为“家庭设置”，但现实上已承担“未加入家庭用户的创建/加入承接页”职责，未加入家庭的 child 用户也允许进入并输入邀请码加入

这些入口已经各自可用，但它们只解决“这一步怎么完成”，没有建立完成之后的连续承接。例如：

- 输入邀请码后，用户只知道“确认并继续”，不知道进入后接下来推荐做什么
- 创建家庭后，只会 toast 成功并刷新页面，没有把“下一步添加孩子 / 进入首页”的目标显式呈现

### 问题2：首页空态是纯提示语，不是正式引导结构

当前首页 `pages/index/index.wxml` 中的空态仍然是按条件分支输出几句文本：

- 家长自己视角无孩子：`还没有孩子成员，请前往家庭设置添加孩子`
- 家长看孩子无任务：`点击右下角"+"按钮添加任务`
- 孩子视角无任务：`暂无任务`

问题在于：

1. 这些提示缺少统一层级，不像正式内容区，更像临时提示语。
2. 没有显式 CTA，用户看到“去家庭设置”仍要自己找入口。
3. 和首次进入状态没有关联，导致“老用户正常空态”和“新用户还没完成初始化”的语义混在一起。

### 问题3：当前“首次启动”只有欢迎消息，没有页面级承接

`utils/app/post-login-bootstrap.js` 已存在 `isFirstLaunch` 检查，并会创建一条欢迎系统消息。但它目前存在两个局限：

1. 欢迎消息是消息中心内容，不是用户当下操作路径的一部分。
2. 它不关心用户是否已加入家庭、是否已有孩子、是否已有任务或奖励。

因此它适合作为“欢迎语”，不适合作为 `M22E` 的核心引导承载。

### 问题4：空态设计经验已经存在，但还没有提升为统一规则

奖励页在 `M14A` 已经建立过“显式空态卡 + 角色差异 + 明确 CTA”的正式经验，表现项管理页在 `M22G` / `M22H` 又收口过“单一提示来源”和“避免重复解释”的设计规则。但这些经验还没有成为跨页面统一原则：

- 哪些空态应该是卡片而不是一行文案
- 哪些空态应该给主 CTA，哪些只给解释
- 首次进入空态和普通空列表如何区分

`M22E` 需要把这些经验统一到新用户上手路径里。

## 技术方案

### 方案概述

`M22E` 采用“轻量阶段模型 + 页面原位承接”的方案，不做新页面堆叠，不引入重型引导框架：

1. **建立正式的 onboarding 阶段判断模型**
   - 统一判断用户当前所处阶段
   - 区分“首次进入中的未完成状态”和“普通空态”
2. **在现有关键页面原位表达下一步**
   - `access-gate` 负责“进入前确认”和“进入后会发生什么”
   - `family-settings` 负责“家庭还没建立 / 刚建立后的下一步”
   - 首页负责“当前家庭已建立后的下一步”
3. **通过一次性承接上下文把跨页引导串起来**
   - 邀请进入或刚加入家庭后，不依赖用户自己回忆前一步
   - 由页面根据短期上下文展示一次性的承接卡片

整体目标是：让用户每次只面对一个最值得做的下一步，而不是同时看到一堆按钮和提示语。

### 核心设计决策

#### 决策1：不做全屏 onboarding，改用页面内引导卡片

`M22E` 不新增启动全屏教学页，不做浮层式逐步教程，而是在用户本来就要去的页面上做原位引导。

原因：

- 当前小程序已经有 `access-gate`、`family-settings`、首页三处天然承接点
- 用户目标是尽快完成创建家庭、加入家庭、添加孩子、创建任务，不是学习一套操作手册
- 全屏 onboarding 容易和邀请进入、自动登录、系统只读等真实状态冲突

最终形态：

- `access-gate`：确认卡 + 后续说明
- `family-settings`：无家庭引导卡、创建成功后的下一步卡
- 首页：阶段卡片替代纯文本空态

#### 决策2：首次进入阶段以“真实业务状态”为准，不仅依赖 `isFirstLaunch`

`isFirstLaunch` 只能回答“是不是第一次打开过应用”，不能回答“用户现在还差哪一步”。

`M22E` 的阶段判断以业务真相为准：

- 是否已加入家庭
- 是否是家长 / 孩子
- 家庭中是否已有孩子成员
- 当前视角下是否已有任务
- 家长视角下是否已有正式奖励

`isFirstLaunch` 只作为辅助信号：

- 控制一次性欢迎卡/提示是否需要更强强调
- 不作为核心业务阶段的唯一判断条件

#### 决策3：新增轻量 onboarding 状态解析 helper，不新增后端接口

本期不新增后端 API，阶段解析全部基于现有前端已能获得的数据完成。

建议新增纯前端 helper：

- `utils/app/onboarding-state.js`

职责：

- 基于 `loginUser / currentUser / family / members / tasks / rewards / isFirstLaunch / pendingOnboardingContext`
  解析当前页面应展示的 onboarding stage
- 输出统一结构：

```javascript
{
  stage: 'no_family_parent',
  title: '先创建你的家庭',
  description: '创建后才能添加孩子、安排任务和一起协作。',
  primaryAction: { type: 'create_family', text: '创建家庭' },
  secondaryAction: { type: 'join_with_code', text: '输入邀请码加入' },
  emphasis: 'first-entry'
}
```

该 helper 必须保持纯函数，不在内部直接做 `wx.navigateTo` 或存储写入。

#### 决策4：跨页的一次性承接使用 app 级临时上下文，不写长期存储

邀请进入、加入家庭、创建家庭成功后，需要在下一页展示“一次性下一步提示”。

这类状态不适合长期存储，建议通过 `app.globalData.pendingOnboardingContext` 传递：

```javascript
{
  source: 'invite_join_family',
  familyId: 'fam_xxx',
  createdAt: 1714270000000
}
```

规则：

- 仅用于一次性承接
- 被目标页消费后即清空
- 不写入 `wx storage`
- 最长只保留当前登录会话；若上下文丢失，页面应退化为基于真实业务状态的普通阶段判断，不能阻塞主流程

这样可以避免为 `M22E` 再引入一套新的持久化状态，同时也不把一次性 UX 信号混进用户模型。

#### 决策5：首页阶段卡片成为“家庭建立之后”的主引导承接点

当用户已进入系统后，首页是最稳定、最高频的承接页，因此阶段卡片应放在首页任务区上方，作为正式内容块，而不是 toast 或弱提示。

首页阶段卡片优先处理以下场景：

1. `family_no_child`
   - 家长已建/已加入家庭，但还没有孩子成员
   - 主 CTA：去家庭设置添加孩子
2. `child_no_task_parent_view`
   - 已有孩子，但当前孩子暂无任务
   - 主 CTA：创建第一个任务
   - 次 CTA：去奖励页配置奖励（可选）
3. `child_no_task_child_view`
   - 孩子视角暂无任务
   - 只展示解释文案，不给管理类 CTA

首页原有纯文本空态保留为兜底，但正式阶段卡片优先级更高。

#### 决策6：首页阶段卡片只在“当前任务主视图”显示，不侵入搜索/历史浏览

首页当前已经存在以下正式区块：

- 日期导航与任务主列表
- 奖励进度卡
- 表现记录区
- 搜索面板 / 消息预览等覆盖式交互

因此 `M22E` 不能把 onboarding 卡当成全局常驻提示，而要严格限制显示边界：

- 仅在首页主任务列表场景显示
- 仅在 `isViewingToday === true` 时显示
- 搜索面板展开、消息预览展开、未来日期浏览时不显示
- 命中阶段卡时，原任务空态文案降级或隐藏，避免一页里出现两套“下一步”

这样可以保证 onboarding 卡是“当前任务页的下一步提示”，而不是对整个首页做视觉抢占。

#### 决策7：奖励页空态经验复用，但不在本期大改奖励页

奖励页已经在 `M14A` 建立了较成熟的空态卡片机制，本期不重写奖励页结构，只复用其设计规则：

- 空态是正式卡片，不是一行字
- 家长视角可以有 CTA
- 孩子视角只做解释
- 不重复表达同一件事

`M22E` 只在首页和家庭页补“何时引导去奖励页”的逻辑，不再次进入奖励页大规模视觉重构。

### 阶段模型

建议首期正式支持以下阶段：

| 阶段 | 触发条件 | 主要承接页 | 主 CTA |
|------|---------|-----------|--------|
| `no_family_parent` | 家长未加入家庭 | `family-settings` | 创建家庭 |
| `no_family_child` | 孩子未加入家庭 | `family-settings` / `access-gate` | 输入邀请码加入 |
| `joined_from_invite` | 刚通过邀请码进入或加入家庭 | 首页 / `family-settings` | 继续下一步 |
| `family_no_child` | 家庭已建立但没有孩子成员 | 首页 | 添加孩子 |
| `child_no_task_parent_view` | 家长当前孩子暂无任务 | 首页 | 创建第一个任务 |
| `child_no_task_child_view` | 孩子视角暂无任务 | 首页 | 仅解释，无 CTA |
| `stable_none` | 已过最小可用路径 | 各页不展示 onboarding 卡 | 无 |

说明：

- “没有奖励”不是独立 onboarding 阶段，只作为家长视角 `child_no_task_parent_view` 的次级建议。
- 后续若 `M22E` 实施后发现“先配置奖励”的引导收益更高，可在二次评审中调整为独立阶段。
- 首页阶段只在“当前主任务视图”求值；过去日期、未来日期、搜索态和消息覆盖态不进入该阶段判断。

### 阶段优先级

为避免页面同时命中多个阶段，首期固定优先级如下：

1. `joined_from_invite`
2. `no_family_parent` / `no_family_child`
3. `family_no_child`
4. `child_no_task_parent_view` / `child_no_task_child_view`
5. `stable_none`

约束：

- 一次只允许输出一个主阶段
- `joined_from_invite` 只负责一次性承接，不负责长期空态
- 若同一页面可同时推导出“刚加入家庭”和“没有孩子成员”，优先先解释“你刚完成了什么”，再把下一步指向“添加孩子”

### 页面设计

#### 1. `access-gate`

现有四态机保持不变，只增加更明确的后续承接：

- `share_pending_login`
  - 若是家庭邀请码：明确说明“进入后会加入某家庭，之后可直接开始使用”
  - 若是新用户邀请码：明确说明“进入后可创建自己的家庭，或再加入别人的家庭”
- `confirm_join_family`
  - 确认加入后写入 `pendingOnboardingContext = { source: 'invite_join_family' }`
- `no_action_needed`
  - 若用户已在目标家庭中，不只说“无需继续”，还要解释当前推荐下一步

实现约束：

- 不新增第五种主 mode，继续复用现有四态
- 一次性承接上下文只在“真实完成进入/加入动作”后写入，预览成功本身不写入
- `no_action_needed` 只补解释，不把它重新膨胀成第二套 onboarding 页面

#### 2. `family-settings`

该页在 `M22E` 中应被重新表述为“家庭设置 / 加入家庭承接页”，而不是继续抽象成纯家长管理页。

未加入家庭态从“孤立空态”升级为“路径起点”：

- 家长：
  - 主按钮：`创建家庭`
  - 次按钮：`输入邀请码加入`
- 孩子：
  - 只保留 `输入邀请码加入`
- 不再在未加入家庭态出现与当前身份不一致的 CTA
- `邀请码中心` 仍按现有权限规则控制，只是次级入口，不进入未加入家庭主引导链路

新增“刚完成家庭创建/加入”的承接卡片：

- 刚创建家庭：提示“下一步添加孩子，才能开始安排任务”
- 刚加入家庭且是查看者家长：提示“你已加入家庭，可先查看进展；如需协助管理，由管理员调整权限”

实现约束：

- 不改变“已加入家庭的孩子不进入家庭设置管理态”的既有业务限制
- 只修正文案层级和承接卡片，不在本期重做家庭成员列表、邀请码中心或 PIN 设置的信息架构
- 创建家庭成功后写入 `pendingOnboardingContext = { source: 'create_family' }`，以便首页和本页都能消费“下一步添加孩子”的一次性提示

#### 3. 首页

新增正式 onboarding 卡片区域，位于任务列表上方、日期导航下方或附近稳定区域，由具体视觉评审决定。

要求：

- 卡片只输出一条主要结论和一个主 CTA
- 不与原有空态文本重复表达
- 一旦命中阶段卡片，原纯文本空态应降级或隐藏
- 不改变奖励进度卡、表现记录区和浮动创建入口的职责
- 当前若处于过去/未来日期浏览，只保留原有日期语义，不显示 onboarding 卡片

示例：

- `family_no_child`
  - 标题：`先把孩子加进家庭`
  - 说明：`添加后，才能按孩子视角安排任务、记录表现和累积奖励。`
  - CTA：`去添加孩子`
- `child_no_task_parent_view`
  - 标题：`给孩子安排第一个任务`
  - 说明：`从一个简单任务开始，孩子就能看到今天该做什么。`
  - CTA：`创建任务`
  - 次 CTA：`去看看奖励`

首页 CTA 约束：

- `去添加孩子`：跳转到 `family-settings`
- `创建任务`：复用现有首页创建入口，不新增平行入口页
- `去看看奖励`：仅作次级建议，不得抢占主 CTA
- 孩子视角不输出管理型 CTA

#### 4. 欢迎消息

欢迎消息继续保留，但降级为补充说明，不承担主引导职责。

可选优化：

- 调整欢迎消息文案，使其与 `M22E` 的最小可用路径一致
- 避免继续输出“先设置奖励，再创建任务”这种过强顺序要求，改为更中性的建议

### 一次性承接上下文契约

建议首期仅支持以下 `source`：

| source | 写入时机 | 可消费页面 | 目标提示 |
|--------|---------|-----------|---------|
| `invite_join_family` | 已登录用户确认加入家庭成功后 | 首页 / `family-settings` | 解释“已加入家庭”，并给出下一步 |
| `guest_invite_entered` | 未登录用户通过邀请码完成进入后 | 首页 | 解释“已进入小程序”，并给出下一步 |
| `create_family` | 创建家庭成功后 | 首页 / `family-settings` | 解释“家庭已创建”，并指向添加孩子 |

消费规则：

- 页面在 `onShow` 或等价刷新点读取
- 一旦决定展示一次性承接卡片，立即消费并清空
- 若页面判断当前已不适合显示该提示，可主动丢弃，不回写长期状态
- 不允许把该上下文作为业务真相来源；业务真相仍来自 `family / members / tasks / role`

## 视觉与交互规格

### 设计目标

`M22E` 的视觉交互目标不是“把提示做得更显眼”，而是让新用户在现有页面结构里，能一眼识别：

- 当前页面最重要的结论是什么
- 下一步应该点哪里
- 为什么这一步比其他动作更优先

因此，本期视觉设计必须服从三个原则：

1. **轻量插入，不重排首页骨架**
   - 不重做首页奖励进度卡、表现记录区、日期导航和浮动创建入口
   - onboarding 卡片只作为任务主区的轻量承接层
2. **主次清晰，不制造第二焦点**
   - 一张卡只允许一个主 CTA
   - 次 CTA 只能是轻量文本动作或弱按钮
3. **与现有风格同源，不做突兀新皮肤**
   - 延续当前首页、邀请码承接页、家庭页已有的浅底、柔和阴影、蓝色主操作和暖色辅助标题体系

### 风格基线

结合现有页面样式，`M22E` 应沿用以下基线：

- 首页 `index.wxss`
  - 整体是浅灰蓝渐变底
  - 卡片为白底或近白底，阴影轻，避免重描边
  - 主强调色以蓝色为主，辅助强调色为偏暖棕金标题
- 邀请码承接页 `access-gate.wxss`
  - 使用较大的圆角、柔和渐变背景和清晰的主次按钮分层
- 家庭页 `family-settings.wxss`
  - 使用简洁白卡、留白充足、单列堆叠式操作

结论：

- `M22E` 不应引入新的高饱和主题色
- 不应引入强营销感横幅、重阴影浮层或视觉噪点插画
- 应继续使用“白卡 + 浅底 + 蓝色动作”的体系，但在首页中控制存在感，避免压过任务本身

### 信息层级

每张 onboarding 卡片固定为四层结构，不能膨胀：

1. **阶段标签**
   - 可选
   - 用于表达“刚加入家庭”“下一步推荐”等短标签
   - 视觉上应最轻，不得比标题更抢眼
2. **标题**
   - 用户第一眼应读到的结论
   - 长度控制在 8-14 个汉字内，最多两行
3. **说明**
   - 解释为什么要做这一步
   - 长度控制在 1-2 行，最多不超过 36 个汉字的等价信息量
4. **动作区**
   - 一个主 CTA，必要时一个次 CTA
   - 不允许出现三个及以上动作

层级约束：

- 标题必须显著高于说明
- 主 CTA 必须显著高于次 CTA
- 辅助说明、权限解释、只读提示必须降级到卡片底部或次级文本区

### 页面布局规则

#### 1. 首页

onboarding 卡片位置固定为：

- 日期导航之后
- 任务列表标题或列表主体之前
- 仍属于“今日任务主区”的一部分

不能放置的位置：

- 不能放在奖励进度卡上方，避免一进首页就被引导压住
- 不能放在表现记录区之后，避免用户错过
- 不能做悬浮层、吸顶条或底部悬浮条

间距规则：

- 与日期导航之间保留清晰分组间距
- 与任务列表之间保持比普通段落更大的分隔，但不要大到像另一页内容
- 卡片上下间距应与首页既有 card 间距体系一致，避免突兀断层

#### 2. `family-settings`

未加入家庭态和“刚完成创建/加入”承接卡应遵循单列堆叠布局：

- 承接卡位于页面主内容上半区
- 创建/加入主动作紧跟说明出现
- 不把“邀请码中心”与主链路按钮并列提升为同等级动作

#### 3. `access-gate`

承接说明继续放在现有卡片内部，不新增第二张平行卡片：

- 邀请码摘要卡仍是主体
- “进入后会发生什么”的说明作为摘要卡下方补充区
- “无需继续”态只补充推荐下一步，不形成新的重卡片

### 卡片视觉规格

#### 1. 卡片容器

- 使用白底或近白底卡片
- 圆角应与现有首页卡片同一等级，偏柔和，不要尖锐矩形
- 阴影要轻，优先使用低对比阴影而不是重边框
- 可以使用很轻的蓝灰描边或内阴影辅助分层，但不做高对比描边

#### 2. 标题与说明

- 标题颜色应接近现有主文本色，不使用纯黑
- 说明文字沿用当前次级文字灰度
- 阶段标签可用低饱和浅蓝底或浅暖底，但透明度要克制

#### 3. 主 CTA

- 延续项目当前蓝色主按钮体系
- 形态应为稳定的圆角实底按钮
- 宽度优先自适应内容，但在首页不要做整行超重按钮

#### 4. 次 CTA

- 仅允许两种形态：
  - 文字按钮
  - 浅底弱按钮
- 不允许与主 CTA 做成同等视觉重量

#### 5. 图形元素

- 本期不新增复杂插画
- 如需图示，只允许使用轻量图标、徽标或极简几何提示
- 图示必须服务于识别，不得成为视觉主角

### 状态表现规则

#### 1. 首次强调态

适用于 `joined_from_invite` 或首次进入的关键一步。

要求：

- 可以比普通空态略强
- 允许出现阶段标签
- 允许说明为什么“你刚完成了什么”

限制：

- 不能比错误态更红、更炸
- 不能用整页级动画或大面积高饱和底色

#### 2. 普通空态引导

适用于 `family_no_child`、`child_no_task_parent_view`、`child_no_task_child_view`。

要求：

- 比首次强调态更稳定、更日常
- 视觉上更接近正式内容卡，而不是提醒条

#### 3. 只读 / 查看者降级态

当用户是 `viewer`、孩子视角或系统只读时：

- 保留解释，不放管理型主 CTA
- 若必须解释限制原因，使用轻量说明文案，不额外叠加警告色大块提示
- “为什么不能做”必须弱于“你现在可以做什么/看到什么”

### 交互规则

#### CTA 行为

- 主 CTA 点击后直接进入对应页面或触发当前已有主流程
- 次 CTA 不得打开新的复杂分支流程
- 卡片本身不做“整卡可点”，避免误触

#### 一次性承接消费

- 点击主 CTA 前后都不应导致卡片闪烁重建
- 一次性承接卡一旦被消费，不应在同一次页面停留中反复出现
- 若用户返回原页，应由真实业务状态决定是否切换到普通阶段卡，而不是继续显示旧的“一次性完成提示”

#### 切换稳定性

- 阶段卡切换必须避免页面高度骤变造成的跳动
- 首页如果从 `family_no_child` 切到 `child_no_task_parent_view`，应尽量保持卡片容器高度接近
- 如文案长度不同，优先通过固定最小高度和按钮区留白控制视觉稳定性

### 动效与过渡

本期只允许低干扰动效：

- 卡片首次进入可用轻微淡入或上浮
- CTA 点击遵循现有按钮按压反馈
- 不做连续脉冲、弹跳、闪烁、轮播式提示

动效原则：

- 动效服务于“进入”和“状态切换被感知”
- 不能让用户觉得页面在抖、跳、眨眼

### 文案与长度约束

- 标题：优先短句，不写并列句
- 说明：只解释一层原因，不写产品说明书式段落
- 按钮文案：优先动词开头，如“创建家庭”“去添加孩子”“创建任务”
- 权限说明：避免长句堆叠，必要时拆成独立次级说明

### 小屏与极端内容约束

需要在设计阶段提前考虑以下情况：

- 家庭名称较长
- 用户昵称较长
- 说明文案因身份不同而多 1 行
- 小屏设备下日期导航、阶段卡、任务标题连续出现

约束：

- 卡片不得因长标题撑成异常高块
- 按钮区允许换行，但主 CTA 与次 CTA 不能互相挤压
- 不依赖固定英文宽度或超窄按钮

### 视觉验收标准

设计实施后，至少满足以下验收口径：

- 用户进入首页时，第一眼仍然知道“这里是任务页”，不是被 onboarding 接管
- 命中阶段卡时，用户能在 3 秒内看懂“下一步是什么”
- 同一页面不存在两个同等级主动作互相竞争
- 卡片与现有首页、邀请码页、家庭页风格一致，没有单独长出一套新皮肤
- 阶段切换时页面不出现明显跳动、闪烁或高度突变

| 阶段判断条件过多，页面再次各自分叉 | 引导逻辑失控 | 中 | 将阶段解析集中到单一 helper，页面只消费结果 |
| 一次性承接上下文未正确清空 | 用户反复看到旧提示 | 中 | 采用“读取即消费”规则，并补单元测试 |
| 首页卡片与原空态并存，信息重复 | 页面显得啰嗦 | 高 | 卡片命中时压低或隐藏原纯文本空态 |
| 把“首次进入”做得过重 | 影响老用户和频繁使用体验 | 中 | 坚持页面内轻量承接，不做全屏教学 |
| 奖励配置是否应先于任务创建存在争议 | 引导顺序不稳定 | 中 | 首期只把奖励作为次级建议，不设置为硬前置 |
| 首页已有奖励/表现/日期结构较满 | 新卡片抢占视觉层级 | 中 | 将卡片限定为任务主区轻量承接，不新增重型主视觉 |
| `family-settings` 现有角色边界理解不清 | 文案和 CTA 出现身份冲突 | 中 | 设计中明确区分“未加入家庭承接态”和“已加入家庭管理态” |

## 替代方案

### 方案A：新增独立 onboarding 页面或全屏引导流程

**优点**：
- 表达集中，讲解空间大
- 可一次性覆盖更多规则说明

**缺点**：
- 与邀请码进入、自动登录、系统只读、已存在家庭等真实状态容易冲突
- 需要额外维护退出/跳过/回访逻辑
- 与当前小程序轻量体验目标不一致

**结论**：不采用。

### 方案B：继续保持现有分散文案，只补几句提示

**优点**：
- 改动最小
- 短期实现成本低

**缺点**：
- 无法真正形成连续路径
- 首页、家庭页、承接页仍会各说各话
- 很容易在后续 `M22C` 前再次积累碎片化逻辑

**结论**：不采用。

### 方案C：采用“阶段 helper + 页面原位卡片”的轻量方案

**优点**：
- 对现有页面结构侵入小
- 能建立统一阶段模型
- 更符合当前项目的原生小程序信息密度与维护成本

**缺点**：
- 需要较严格的阶段边界设计
- 需要页面间共享一次性承接上下文

**结论**：采用本方案。
