## 需求分析

### 功能描述

当前项目已经进入真实用户使用阶段，系统管理员已经可以在后台看到真实用户正在正常使用，但用户侧缺少一个浅层、稳定、明确的“如何联系维护者”入口。现有 About 页虽然已经具备版本信息和隐藏式管理员入口，但入口过深，普通用户很难自然发现，也不适合作为唯一帮助入口。

本期目标不是引入复杂客服系统，也不是构建在线工单或留言后台，而是在不破坏当前 About 页行为的前提下，新增一个用户容易找到的“帮助与反馈”入口，并在 About 页中正式展示维护者联系方式，支持用户在遇到问题、权限异常、邀请码异常或产品需求时快速联系维护者。

### 业务价值

- [x] 用户价值：用户在遇到问题时可以快速找到维护者联系方式，不必通过试错去寻找入口。
- [x] 产品价值：降低真实使用中的沟通摩擦，让系统管理员能更快获得问题反馈和需求反馈。
- [x] 技术价值：用轻量静态信息方案建立正式反馈入口，为未来是否做管理员可配置或在线留言留出扩展点。

### 功能范围

**包含**：
- ✅ 新增全局可达的“帮助与反馈”入口
- ✅ 保留现有 About 页功能，同时增加“联系维护者”信息区块
- ✅ 在 About 页中展示：
  - 微信二维码
  - 微信号文本
  - 邮箱
  - 简短反馈说明文案
- ✅ 支持复制微信号和邮箱
- ✅ 保留现有版本信息和版本区连续点击 7 次进入管理员页的行为

**不包含**：
- ❌ 不做在线留言/工单系统
- ❌ 不做后端数据库存储联系方式
- ❌ 不在本期支持系统管理员在线修改联系方式
- ❌ 不新增消息中心“联系客服”双向对话能力
- ❌ 不改动现有系统管理员入口策略

### 优先级

- **优先级**：P1
- **理由**：这不是核心业务链路功能，但已经直接影响真实用户能否顺畅反馈问题，且实现成本低、收益明确。

## 技术方案

### 方案概述

本期采用“**浅入口 + 复用 About 页 + 静态配置**”方案：

1. **在首页用户切换面板新增“帮助与反馈”入口**
   - 用户从首页左上角头像进入用户面板后，可以直接看到帮助入口
   - 不要求用户先进入家庭设置页再找到 About 页

2. **保留并扩展 About 页**
   - About 页继续承担：
     - 版本信息展示
     - 版本区 7 连击管理员入口
   - 新增“联系维护者”卡片，使其升级为“帮助与反馈页”

3. **联系方式采用静态资源和静态配置**
   - 微信二维码图片作为前端静态资源放入仓库
   - 微信号文本、邮箱、反馈说明通过轻量配置模块提供
   - 本期不引入后端配置和数据库

这样可以以最低风险快速上线，同时保留后续扩展为管理员可配置项的空间。

### 核心设计决策

#### 决策1：新增浅入口，但不替换 About 页

当前 About 页入口位于家庭设置页底部，用户发现路径过深。  
本期不删除现有入口，而是在用户切换面板底部新增“帮助与反馈”入口，形成双入口结构：

- 首页头像 → 用户切换面板 → 帮助与反馈
- 家庭设置页底部 → 帮助与反馈

选择理由：
- 首页头像入口是当前最浅、最稳定、全局可达的用户个人入口
- 不需要在首页主界面上增加新的常驻按钮，避免打扰主任务流
- 保留现有家庭设置页入口，兼容已有认知
- 帮助入口属于通用支持入口，必须独立于“添加成员”权限显示，不能复用仅管理员可见的展示条件

#### 决策2：保留现有 About 页行为，新增帮助内容区块

About 页现有三项价值不能破坏：

1. 版本信息展示
2. 版本行连续点击 7 次进入管理员页

因此本期不重构 About 页为完全新页面，而是新增“联系维护者”卡片。页面建议顺序如下：

1. 应用信息（现有 hero 卡片）
2. 联系维护者
3. 版本信息

选择理由：
- 应用名称与简介仍然有保留价值，不应在本次帮助入口迭代中被顺手删除
- 联系信息放在应用信息之后、版本信息之前，用户更容易第一眼看到
- 版本和管理员暗门逻辑仍位于原来的“版本信息”区域，不改变行为语义

#### 决策3：移除小程序二维码，仅保留维护者联系方式二维码

当前阶段的核心目标是让用户能快速找到维护者并发起反馈，而不是在 About 页继续承担小程序传播入口。  
因此本期移除 About 页中的小程序二维码展示，只保留维护者微信二维码：

- 微信二维码：用于联系维护者

选择理由：
- About 页将聚焦“帮助与反馈”主语义，避免页面信息分散
- 当前用户反馈场景下，联系方式优先级高于传播入口
- 可减少页面噪音，让用户更快识别该去哪里求助

#### 决策4：联系方式必须同时展示二维码和文本

仅展示微信二维码不够，因为用户往往就在微信中打开小程序，无法方便地扫描自己手机上的二维码。  
因此本期联系方式区必须至少包含：

- 微信二维码图片
- 微信号文本（可复制）
- 邮箱文本（可复制）

选择理由：
- 同机使用场景下，文本复制比扫码更可用
- 邮箱作为备用渠道，可覆盖无法使用微信添加的情况

#### 决策5：本期采用静态配置，不做系统管理员在线配置

虽然未来可以把联系方式做成系统管理员可配置，但本期不建议引入后端配置链路。  
本期使用前端静态配置模块，例如：

```javascript
module.exports = {
  supportTitle: '联系维护者',
  supportHint: '遇到使用问题、权限异常或需求反馈，都可以联系我',
  wechatId: 'your_wechat_id',
  email: 'support@example.com',
  wechatQrImage: '/packageManage/assets/about/support-wechat-qrcode.png'
};
```

选择理由：
- 这是一个轻量文案/静态资源型功能，不值得先引入后端字段、系统管理表单和鉴权链路
- 当前需求已明确，静态配置足以满足第一阶段上线
- 后续如确有频繁修改联系方式的需求，再升级为管理员配置

#### 决策6：用户切换组件只负责抛事件，页面层负责关闭与跳转

当前 `user-switcher` 组件的显示与关闭由父页面控制，组件内部关闭方法本质上只是发出 `close` 事件，并不直接完成遮罩与动画收尾。  
因此本期不建议在组件内部直接执行 `wx.navigateTo`，而是采用“组件发事件，父页面处理导航”的方式：

- `user-switcher` 组件新增 `helpFeedback` 事件
- 首页收到事件后，先隐藏 `showUserSwitcher`
- 等待当前关闭动画完成后，再由首页统一执行 `wx.navigateTo`

选择理由：
- 与当前组件职责边界一致，避免把页面导航职责塞进展示组件
- 更容易保证关闭动画、遮罩收起和页面跳转顺序正确
- 便于后续在其他页面复用同一个组件事件语义

时序约定：

- 当前 `user-switcher` 关闭动画时长约为 `220ms`
- 帮助入口跳转链路应先触发关闭，再等待关闭动画完成后跳转
- 若后续调整 `user-switcher` 关闭动画时长，需同步更新帮助入口跳转等待时长

#### 决策7：联系方式缺失时采用降级展示，而不是空白占位

虽然本期采用静态配置，但仍需定义缺省行为，避免资源或字段缺失时页面表现异常。  
建议约定如下：

- `wechatQrImage` 缺失：隐藏二维码预览区，仅展示微信号文本和邮箱
- `wechatId` 缺失：隐藏微信号行，不展示空值
- `email` 缺失：隐藏邮箱行，不展示空值
- `supportHint` / `supportResponseHint` 缺失：回退到默认文案

选择理由：
- 让页面在配置不完整时仍可正常使用
- 降低静态资源遗漏导致整页体验异常的风险
- 便于后续分阶段接入或替换联系方式

#### 决策8：维护者微信二维码不依赖小程序运行环境

现有 About 页中的小程序二维码曾按正式环境控制显示，但维护者联系方式二维码不应继承该规则。  
本期约定：

- 维护者微信二维码与 `release / trial / develop` 环境无关
- 只要 `wechatQrImage` 配置存在，就正常展示并可预览
- 仅当 `wechatQrImage` 缺失时，才按降级规则隐藏二维码区

选择理由：
- 联系方式属于支持信息，不应因当前构建环境不同而消失
- 便于开发、体验、正式环境一致验证帮助与反馈能力
- 避免误复用现有小程序二维码的正式环境判断逻辑

### 交互设计

#### 1. 用户切换面板入口

在现有 `components/user-switcher/` 面板底部新增次级入口：

- 标签：`帮助与反馈`
- 说明：`遇到问题时可联系维护者`
- 点击后进入：`/packageManage/pages/about/about`

设计要求：
- 不与“添加成员”按钮混成同一个主操作按钮
- 视觉上应为次级入口，不抢占“切换用户 / 添加成员”的主语义
- 必须独立于“添加成员”权限渲染，对普通成员、查看者、只读用户也可见
- 组件点击后不直接 `navigateTo`，而是触发 `helpFeedback` 事件，由父页面统一关闭面板并跳转

#### 2. About 页帮助卡片

新增卡片区块：

- 标题：`联系维护者`

- 微信号行：点击复制
- 邮箱行：点击复制

```javascript
// utils/support-contact.js
module.exports = {
  supportTitle: '联系维护者',
  supportHint: '遇到使用问题、权限异常或需求反馈，都可以联系我',
  supportResponseHint: '建议描述问题现象，必要时附上截图',
  wechatId: '...',
  email: '...',
  wechatQrImage: '/packageManage/assets/about/support-wechat-qrcode.png'
};

// components/user-switcher/user-switcher.js
methods: {
  navigateToHelpFeedback() {
    this.triggerEvent('helpFeedback', {});
  }
}

// pages/index/modules/index-user-switcher.js
function handleHelpFeedback(page) {
  page.setData({
    showUserSwitcher: false
  });
  setTimeout(() => {
    wx.navigateTo({
      url: '/packageManage/pages/about/about'
    });
  }, 220);
}

// packageManage/pages/about/about.js
Page({
  onLoad() {
    // 保留现有版本/环境逻辑
    // 新增加载 support-contact 配置
    // 缺失字段时按降级规则展示
  },
  onSupportWechatIdTap() {
    // 复制微信号
  },
  onSupportEmailTap() {
    // 复制邮箱
  },
  onSupportQrcodeTap() {
    // 预览微信二维码
  }
});
```

### 关键函数

**函数1**：`navigateToHelpFeedback`
- **输入**：无
- **输出**：无
- **职责**：从用户切换面板发出帮助入口事件
- **依赖**：组件事件系统

**函数2**：`handleHelpFeedback`
- **输入**：页面实例、事件对象
- **输出**：无
- **职责**：父页面统一关闭用户面板，并在关闭动画完成后跳转帮助与反馈页
- **依赖**：`wx.navigateTo`

**函数3**：`onSupportWechatIdTap`
- **输入**：无
- **输出**：无
- **职责**：复制微信号文本
- **依赖**：`wx.setClipboardData`

**函数4**：`onSupportEmailTap`
- **输入**：无
- **输出**：无
- **职责**：复制邮箱文本
- **依赖**：`wx.setClipboardData`

**函数5**：`onSupportQrcodeTap`
- **输入**：无
- **输出**：无
- **职责**：预览维护者微信二维码
- **依赖**：`wx.previewImage`

## 替代方案

### 方案A：只在 About 页增加联系方式，不新增浅入口

**优点**：
- 实现最简单
- 改动最少

**缺点**：
- 用户仍然很难发现入口
- 不能解决“About 页过深”的核心问题

**结论**：不采用。本期核心问题不是 About 页内容不够，而是入口太深。

### 方案B：首页常驻悬浮“联系客服”按钮

**优点**：
- 极易发现

**缺点**：
- 打扰主任务流
- 与当前任务管理产品界面气质不符
- 对真实问题量未知阶段来说过重

**结论**：不采用。当前阶段优先做浅入口，而不是高打扰入口。

### 方案C：直接做在线留言/反馈表单

**优点**：
- 用户反馈闭环更完整

**缺点**：
- 需要新增后端接口、数据表、治理页面和通知机制
- 实现复杂度远高于当前需求

**结论**：不采用。当前先做可直接联系维护者的轻量方案。
