## 技术方案

### 方案概述

`M21C` 采用“只修正文档事实漂移，不借题发挥扩项”的方案：

1. 先以当前代码为准，确认哪些文档描述已经不再准确。
2. 只更新高频入口文档，不做全仓文档大扫除。
3. 把文档表述从“硬编码规范”调整为“以当前正式主题 token / 页面语义 / 编排约束为准”。

这样可以保证：

- 文档重新可信
- 设计和评审口径变得稳定
- 不把低 ROI 的代码优化混进当前里程碑

### 关键设计决策

#### 决策1：本期按“事实同步”而不是“规范重设计”执行

本期目标是把文档修到“反映当前正式代码事实”，而不是顺手再定义一套新的 UI 规范或页面性能规范。

因此：

- 如果当前代码实现存在多处不同口径，但尚未进入统一治理里程碑，本期文档应如实描述现状和检查原则，而不是替代码强行定输赢。
- 真正的颜色统一、页面拆分和加载编排优化，留给后续代码治理型里程碑。

#### 决策2：架构文档只补明确缺失事实，不重写整份架构说明

当前已经确认：

- `ConfigService` 已存在于架构文档
- `AnalysisBoardService` 缺失

所以本期只补齐后者，并保持与 `services-guide` 中“分析页专用、非 ServiceManager 注册实例”的现状一致。

这里冻结两条实施约束：

- 不把 `AnalysisBoardService` 写进“通过 ServiceManager 统一管理和依赖注入”的正式服务清单中
- 架构文档必须把它表述为“分析页按需调用的页面侧聚合模块 / 服务层特例”，并与 `AnalyticsService` 区分开

对应地，实施时需要同步修正架构文档中的总述句，避免形成：

- 上文把 `AnalysisBoardService` 记为普通服务
- 下文又说“所有服务都通过 ServiceManager 统一管理”

这种新的自相矛盾

#### 决策3：UI 检查口径改为“检查语义一致性”，不再写死过时 hex

当前高频文档里写死的任务类型颜色与真实实现不一致。若继续保留固定 hex，会导致：

- 审查者把“历史口径”误当作“当前权威实现”
- 后续每次 UI 评审都把注意力浪费在错误基线

因此本期调整为：

- 页面涉及任务类型色时，应与当前正式主题 token 和所在页面的既有视觉语义保持一致
- 若某类页面存在局部差异，实现是否统一应进入独立 UI 治理里程碑评估，不在本期直接判错

本期同时冻结替换后的检查口径，避免实施时改成空泛表述：

- 任务类型颜色检查：
  - 从“学习 `#4285F4`、习惯 `#4CAF50`、兴趣 `#FF9800`”改为“任务类型颜色应与当前正式主题 token 和所在页面既有视觉语义一致，不再以固定 hex 作为全局唯一规则”
- 间距检查：
  - 从“卡片一律 30rpx、标准间距一律 24rpx”改为“优先复用全局 spacing token 与页面既有节奏；若页面已有正式 token 化间距，不再用单一数值对所有页面做硬判”

#### 决策4：性能检查口径改为“避免无意义频繁更新”

`setData` 的风险点不是“出现多次调用”本身，而是：

- 连续更新同一数据域
- 可以合并却被拆成多轮无意义渲染
- 热路径里高频重复触发

首页当前批量加载并不是这种情形，因此文档应强调“避免无意义频繁 `setData`”，而不是把“存在多次 `setData`”直接视为问题。

本期冻结替换后的性能检查口径：

- 从“是否合并 `setData` 调用”改为“是否在同一热路径中对同一数据域进行了可合并却未合并的无意义频繁 `setData` 更新”
- 若属于跨数据域、异步编排或并发加载后的独立状态更新，不因“调用次数大于 1”而直接判错

### 技术选型

| 技术点 | 选择方案 | 替代方案 | 选择理由 |
|--------|---------|---------|---------|
| 文档治理策略 | 只修正事实漂移 | 全仓文档统一大扫除 | 范围小、风险低、ROI 更高 |
| 架构同步 | 精确补齐缺失服务事实 | 重写整份架构文档 | 当前问题集中，不需要扩项 |
| UI 检查修正 | 改为语义与 token 约束 | 继续写死 hex 值 | 避免继续用过时口径做错误审查 |
| 性能检查修正 | 聚焦无意义频繁更新 | “凡多次 setData 必错” | 更符合当前真实实现 |

## 风险评估

### 风险1：把“事实同步”做成“规范重写”

- **风险说明**：如果本期顺手重写过多历史规范，会显著扩项，并让设计评审重新发散到 UI 统一或页面治理。
- **缓解措施**：只修改已确认漂移且高频被引用的入口文档，不处理低频或历史设计文档。

### 风险2：文档先行定义尚未统一的实现细节

- **风险说明**：如果本期直接在文档里强行宣布唯一颜色映射，会造成“文档正确、代码错误”的新错位。
- **缓解措施**：文档只定义检查原则和正式语义，不对尚未进入治理的局部实现做超前裁决。

### 风险3：把性能原则写得过于教条

- **风险说明**：如果继续用“多次 `setData` 必错”这类说法，后续评审仍会误判当前合法编排。
- **缓解措施**：明确性能风险来自无意义频繁更新，而不是调用次数本身。
