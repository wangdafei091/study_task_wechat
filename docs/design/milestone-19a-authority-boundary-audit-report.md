## 1. 审计结论摘要

当前项目不是“前端和后端完全重复、可直接二选一”的状态，而是一个已经部分后端权威化、但仍保留明显本地优先特征的混合架构。

首轮审计后可以明确：

- 星星到期结算、正式提醒、必做惩罚、逾期补做退星、奖励兑换/取消兑换，这些高一致性能力在云端模式下已经以后端事务为权威。
- 任务创建、重复任务实例展开、补云与回灌、本地仓储缓存、离线降级、provisional message、分析页聚合，仍有大量前端主导或混合协作职责。
- 当前最值得继续治理的不是“删掉前端逻辑”，而是优先处理高漂移风险的混合区。

## 2. 能力边界矩阵

| 审计对象 | 业务能力 | 当前归属 | 现状结论 | 漂移风险 |
|---------|----------|----------|----------|----------|
| 配置 | API 模式开关与降级分流 | 前端主导 | `utils/api-config.js` 通过 `ENABLE_API + API_BASE_URL => finalApiEnabled` 决定是否触发所有后端权威链路 | P1 |
| 用户上下文/权限 | 登录用户、当前视角、消息/分析范围 | 混合协作 | 前端用 `loginUser/currentUser` 和 `view-scope` 决定读视角，后端再用 `targetUserId/actorUserId/actorRole/familyId` 做最终授权和记述落库 | P1 |
| 任务 | 创建/编辑/删除 | 混合协作 | 前端本地先写、打 `pendingSyncMeta`、失败保留待同步；后端负责正式持久化和消息 | P1 |
| 任务 | 完成/重置 | 后端权威 | 云端模式下通过 `PATCH /api/tasks/:taskId/status` 由后端执行状态变更、补做退星/回滚、正式消息 | P1 |
| 任务 | 必做惩罚 | 后端权威 | 前端只负责触发 `/api/tasks/penalties/sync`，惩罚本身由后端事务执行 | P1 |
| 任务 | 重复任务实例展开 | 前端主导 | `services/task-service/task-repeat.js` 仍负责日期展开、本地落库、批量补云 | P1 |
| 任务 | 补云、ownership 修正、modifyTime 保护 | 混合协作 | `task-sync.js` 仍承担大量历史兼容和本地保护逻辑 | P1 |
| 星星 | 到期结算 | 后端权威 | 前端只触发 `expiry-authority/sync` 并用云端结果覆盖本地同步快照 | P1 |
| 星星 | 消费/扣减 | 后端权威 | 云端模式下奖励兑换、惩罚、补做回滚依赖后端事务扣减 | P1 |
| 星星 | 本地加减星、过期保护、即将过期计算 | 本地降级专属 | `ENABLE_API=false` 时，前端仍保留完整星星能力 | P2 |
| 奖励 | 兑换/取消兑换 | 后端权威 | 后端负责扣星、退款、保护计算、正式消息和幂等 | P1 |
| 奖励 | 可兑换列表与保护展示 | 混合协作 | 云端模式依赖后端保护结果；本地模式仍由前端自行计算可兑资格与保护标签 | P2 |
| 奖励 | CRUD 与补云 | 混合协作 | 奖励创建/更新/删除仍保留前端本地写入和补云链路 | P2 |
| 消息 | 正式消息生成 | 后端权威 | 后端根据 action 生成 user/family 双流正式消息并负责去重/折叠 | P1 |
| 消息 | 读取授权与已读/删除 | 后端权威 | 后端按 `viewer + scope + targetUserId` 做严格过滤 | P1 |
| 消息 | provisional message | 本地降级专属 | 仅云同步失败时由前端生成，属于体验兜底而非常态双写 | P2 |
| 分析 | 趋势图/统计聚合 | 前端主导 | 当前没有独立后端分析读模型，前端直接读取本地任务/星星仓储并按视角聚合 | P1 |

## 3. 关键问题清单

### P1-1 任务域存在“后端写权威 + 前端建模/补云主导”的长期混合区

表现：

- 状态更新、惩罚、补做退星已后端权威。
- 但创建、重复实例生成、ownership 修正、modifyTime 保护、本地补并仍在前端。

风险：

- 很容易把“前端仍有很多任务逻辑”误判成“任务域还没后端化”，从而做出过度重构或错误删减。

建议方向：

- 后续优先把任务域拆成独立治理子阶段，不要和消息、分析、离线一起大爆炸处理。

### P1-2 分析页仍是前端读模型，不是后端权威视图

表现：

- `services/analytics-service.js` 基于本地任务、星星流水、星星分组做趋势与统计。
- 当前没有后端“分析聚合接口”或正式分析快照。

风险：

- 用户容易把分析页理解成“后端真实统计”，但它本质上依赖本地缓存与前端聚合。
- 一旦权威余额、家庭范围、过滤口径变化，分析最容易出现认知偏差。

建议方向：

- 把分析域作为后续单独子阶段，不要在没有定义目标读模型前直接硬迁移。

### P1-3 `api-config` 是根开关，任何“后端权威收口”都受离线策略约束

表现：

- `finalApiEnabled=false` 时，大量前端本地逻辑仍必须承担完整业务责任。

风险：

- 如果未来推进“前端瘦身”，但没有先定义离线队列或降级策略，功能会直接退化。

建议方向：

- 后续任何权威归一都必须把配置与离线策略作为前置条件，而不是收尾项。

### P1-4 用户上下文与权限边界已成为多个业务争议的共同根因

表现：

- 前端读视角和后端执行记述都依赖多组身份字段。
- 这层问题并不只属于消息或任务某一域。

风险：

- 很多“家长看到什么、孩子看到什么、谁在代操作”的问题，会被误判成单个业务 bug，而不是上下文边界不统一。

建议方向：

- 需要把这层视为横切基础设施，在后续子阶段中持续复用审计结论。

## 4. 反驳两个常见误判

### 误判 1：前后端核心规则几乎完全重复，因此可以直接删除前端业务层

不成立。

原因：

- 云端高一致性链路确实越来越后端权威，但前端仍承担本地优先、补云、降级、缓存、重复实例展开、分析读模型等正式职责。
- 这些职责不等于“业务规则重复”，很多是混合架构的必要组成。

### 误判 2：既然后端已经接管了星星、奖励、任务状态，剩下只是简单 API 封装

不成立。

原因：

- 任务创建/补云/回灌、奖励 CRUD、分析读模型、provisional message、离线降级都还不是简单转发。
- 真正的难点不在接口数量，而在“哪些职责要留下、哪些职责要继续后移”。

---

## 5. 建议的后续子阶段方向

当前建议先保持 `ROADMAP` 中的 `M19` 总里程碑不拆死，只把后续候选方向记录为审计结论：

| 候选方向 | 建议目标 |
|---------|----------|
| `M19B` 任务域边界收口 | 聚焦重复实例、补云、ownership 修正与本地/云端写路径分工 |
| `M19C` 分析读模型治理 | 明确分析页到底继续前端聚合，还是补后端聚合接口 |
| `M19D` 消息与降级语义治理 | 明确正式消息、provisional message、失败兜底的长期边界 |
| `M19E` 配置与离线队列治理 | 若要继续瘦前端，先定义离线/重放/失败恢复策略 |
