## 需求分析

### 功能描述

`M21L` 已经把表现项做成了“可创建、可记录、可停用、可删除”的正式能力，`M22A` 又进一步补齐了权限与周期护栏。从功能正确性看，表现项主链路已经闭环。

但最近一轮真实体验与验收反馈表明，当前 [`pages/task-occurrence-edit/task-occurrence-edit.js`](/Users/wangdafei/code/study_task_wechat/pages/task-occurrence-edit/task-occurrence-edit.js) 这页虽然“能用”，但还达不到正式交付的成品感：

1. 页面把“已有表现项列表”和“新建/编辑表单”长期并排堆在同一视口里，主次竞争明显。
2. 生效中、未生效、已结束的表现项直接混排，用户要自己逐条读状态，才能判断当前真正可用的是哪些。
3. 历史项默认全部展开，当项目变多后，会把“当前真正要维护的几条表现项”淹没掉。
4. 信息层级偏平，标题、日期、状态、动作都在同一视觉重量上，页面会让人觉得“满、碎、乱”。
5. “新建表现项”虽然可用，但不是一个足够明确的主动作；它和历史维护信息混在一起，不利于低成本上手。
6. 当前设计还没有从“数据增长”和“页面稳定性”角度收口。如果生效中项目本身变多，或者编辑表单在页内展开，页面仍会变长、变吵、变跳。

因此，`M22G` 不再新增表现项能力，而是把当前这页正式收口成一个“极简、易懂、主次清晰”的管理页：

- 默认只突出当前真正有效的表现项
- 让未生效和历史项变成“可理解、可查看、但不抢焦点”的次级信息
- 让“新建表现项”成为稳定、轻量、可预测的主动作
- 让页面在列表变多、创建编辑频繁切换时，仍保持稳定、不跳动、不失焦
- 在不改变后端契约的前提下，提升页面整体精致感和维护效率

在第一版设计落地后的正式评审中，又进一步确认了 5 个需要回写设计稿的结构问题：

1. 头部如果做成强视觉 `hero card`，会让管理页失去克制感，主按钮也会显得过于突兀。
2. `生效中 X 项 · 待生效 X 项 · 历史 X 项` 这种整句式统计摘要不够抗字数增长，长孩子名或更多统计维度下会明显变乱。
3. 虽然 `生效中 / 待生效 / 历史项` 三类语义成立，但把三者作为连续纵向主区块平铺，仍会在长列表场景下拉长页面。
4. 历史项如果同时存在“区块标题 + 摘要行 + 查看动作”，会形成重复表达，视觉上最容易显乱。
5. 卡片内部若继续让 `编辑 / 更多` 并列同权，且正文信息与动作区分隔不足，会带来层级散乱和误触风险。

因此本次文档修订不是推翻 `M22G`，而是在保持“同页管理 + 覆盖式编辑层 + 三类业务语义”不变的前提下，进一步把页面结构收口到更稳、更克制、更抗增长的版本。

在第二轮实现后的真机截图复核里，又确认了一个更本质的问题：当前稿虽然已经不再三段平铺，但页面顶部仍然把“设计意图”直接暴露给终端用户，导致页面看起来依旧不够高级、不够自然。具体表现为：

1. 自定义导航区与头部说明同时存在，顶部承担了“导航 + 解释 + 上下文 + 主动作 + 统计”过多职责，首屏发紧。
2. `当前生效的放上面，其他项目收在次级区域`、`先看当前生效中的项目，其他项目统一收在次级区域，页面更稳也更好找` 这类文案本质是设计说明，不是用户任务信息。
3. 头部统计条如果继续以独立块状存在，会和主区一起争抢注意力，削弱“先进来看当前生效项”的单一重点。
4. 次级容器摘要如果右侧同时给数量和展开符号，容易再次产生“信息重复、看着不利落”的问题。

因此本次修订正式把 `M22G` 从“结构改对”进一步升级为“整页成品化优化”：不仅修分区和交互，还要同时修正文案策略、顶部职责分配、统计的存在方式、卡片动作重量和长列表下的页面稳定性。

在随后两轮真机截图复核里，又进一步确认了 4 个需要纳入正式设计而不是留给实现临场判断的问题：

1. `优先维护现在真正会出现的表现项` 这类句子虽然比旧文案短，但本质仍是设计说明，不适合继续作为主区长期辅助文案。
2. 多孩子且当前孩子无生效项时，区块标题、区块摘要和空态卡容易重复表达同一件事，破坏“极简、清晰”的目标。
3. `其他表现项` 内部如果同时存在 `待生效` 与 `历史项`，会出现两个独立展开入口；设计必须明确这属于“两个独立子列表”，并冻结其视觉表达，避免做成看起来像多余工具按钮。
4. 主按钮虽然需要清晰，但如果饱和度、阴影和尺寸都过重，会再次压过“当前孩子”与主区内容，导致页面右侧抢重心。

因此本次修订继续往下收口：不只禁止解释型文案，还要对区块微文案、空态去重、双入口摘要、主按钮重量和多孩子头部规则给出明确最终方案。

在最新一轮真机截图复核里，又确认了 4 个此前仍留给实现层自由发挥的细部问题，必须继续回写设计冻结：

1. 列表首屏里的 `其他表现项` 在仅有 1 条子入口时，容器高度和留白仍然偏松，容易显得“空”和“悬”。
2. 生效中卡片右侧动作栏虽然已经完成主次分离，但与正文之间仍略显割裂，整体感还不够强。
3. 编辑层顶部 `新建模式 / 新增一条可记录的表现项 / 创建后会自动回到新建项的位置` 三层说明叠加后，页面又从“操作页”退回了“说明页”。
4. 编辑层 `适用时间` 在长期有效场景下同时出现 `开始日期 至 长期有效` 和 `长期有效` 开关，形成重复语义，降低了表单清晰度。

因此本次修订再向前收口一层：不再只修“页面结构”，而是同步冻结编辑层的文案密度、时间表单结构、动作按钮重量，以及次级容器和卡片动作区的空间节奏。

在最新一轮截图复核里，又进一步确认了 4 个更底层的视觉体系问题，必须纳入正式设计，而不能继续靠实现层试错：

1. 编辑层虽然已经去掉说明 banner，但整体控件尺度仍然明显厚于列表页，导致页面像另一套产品语言。
2. 输入框、类别选择、星星步进器、底部操作按钮使用了彼此不一致但都偏大的高度，形成“厚控件叠厚控件”的观感。
3. 编辑层底部主按钮虽然去掉了重渐变，但仍然是高饱和纯色大胶囊，和列表页头部的轻 CTA 不是同一语气，因此依旧突兀。
4. 长期有效场景下，时间区虽然语义已去重，但整个容器仍然显得偏高、偏空，信息密度与表单其余区域不一致。

因此本次修订继续收口到“统一尺寸体系”的层面：不仅要求编辑层说话方式正确，还要确保它和列表页属于同一视觉系统，而不是一个轻列表页里套了一个厚表单页。

在随后对 `1.jpg / 2.jpg / 3.jpg` 的跨页面横向复核里，又确认了一个此前被低估的全局问题：当前稿虽然页内结构已经比旧版清楚，但顶部导航语言仍然明显偏离主流程页面，导致用户会感觉自己像跳进了另一套产品。

具体表现为：

1. `任务管理` 仍使用系统蓝色导航栏，而 `表现项管理` 改成了雾白色自定义头部，页面切换时品牌连续性被打断。
2. 自定义导航、页面背景和首张卡片都偏浅，顶部缺少“这是正式业务页”的稳定起点，首屏容易显得轻飘。
3. 当前方案把“为了接管返回行为而自定义导航”误写成了“视觉上也应该与主流程区别开”，这是错误前提。
4. 用户进入 `任务管理 -> 表现项管理 -> 新建表现项` 是一条连续任务链，头部风格不一致会放大“像跳页面模板”的违和感。

因此本次修订把 `M22G` 的顶部策略正式升级为：**行为可以自定义，但视觉必须统一回主流程导航体系**。  
也就是说，本期不做全站设计系统改造，但 `表现项管理` 至少必须和 `任务管理`、系统导航栏在品牌色、结构语气和页面进入感上属于同一套语言。

### 业务价值

- [x] 用户价值：家长进入页面后能第一眼看到“现在正在用的表现项”，不用再自己筛读历史项。
- [x] 产品价值：把表现项从“功能可用”提升到“成品可交付”，减少页面给人的凌乱感和试错成本。
- [x] 技术价值：把表现项管理页的展示语义、状态分组和交互流程固化下来，降低后续继续叠补丁的风险。

### 事实基线（2026-04-22，基于当前代码与验收反馈）

#### 1. 当前页面是“列表 + 表单”长期同页直出

现状见：

- [`pages/task-occurrence-edit/task-occurrence-edit.wxml`](/Users/wangdafei/code/study_task_wechat/pages/task-occurrence-edit/task-occurrence-edit.wxml)
- [`pages/task-occurrence-edit/task-occurrence-edit.wxss`](/Users/wangdafei/code/study_task_wechat/pages/task-occurrence-edit/task-occurrence-edit.wxss)

当前结构是：

1. 页面说明
2. 孩子切换
3. “已有表现项”卡片
4. “新建/编辑表现项”卡片

这意味着即使用户只是想“看看现在有哪些表现项”，也会立即看到一整套表单。  
页面一打开就进入“列表与表单同时争注意力”的状态，这是当前不舒服的核心原因之一。

#### 2. 当前列表只有逐条状态，没有分组层

当前 `decorateItem()` 只给每条数据打出：

- `有效中`
- `未生效`
- `已停用`

但页面层没有把这些状态再组织成更高一层的信息结构。  
结果就是：

- 1 条有效项和 5 条历史项会被同样展开
- 用户必须逐条读状态标签，才能知道哪些是“当前该关注的”

这与“管理页首屏优先突出当前有效项”的目标不一致。

#### 3. 历史项目前默认和活跃项一样重

当前 `loadItems()` 固定调用：

```javascript
taskService.getOccurrenceTasks({
  date,
  userId: targetUserId,
  includeInactive: true
});
```

这本身没有问题，因为管理页确实需要看到历史项。  
真正的问题是：拿到历史项后，页面没有做“默认收起”或“降权展示”，导致历史项在首屏里和活跃项权重一致。

#### 4. 新建动作存在，但不是单一清晰主动作

当前用户要创建新表现项，只能直接滚到表单区。  
这会带来两个问题：

1. “创建”不是一个明确的主动作按钮
2. 列表与表单没有明显模式切换，用户会不确定自己现在是“在看列表”还是“正在编辑”

#### 5. 当前问题主要是信息架构与交互节奏问题，不是后端能力缺口

从现有实现看，当前后端与服务层已经具备本期所需能力：

- 读取表现项配置列表
- 区分有效项和历史项
- 创建 / 编辑 / 停用 / 删除

因此 `M22G` 应尽量保持为前端页面重构，不引入新的后端契约、数据库字段或额外流程。

#### 6. 当前稿如果仍采用“页内展开表单”，页面跳动风险仍然存在

即使把表单改成“默认收起、按需展开”，只要展开位置仍在页面主流里，就会带来两个问题：

1. 点击“新建”或“编辑”后，列表整体被向下顶开，页面会明显跳动。
2. 当用户编辑完成返回时，滚动位置和注意力容易丢失，页面会显得不稳。

因此本期不能只停留在“是否默认展开”的层面，还必须把“表单承载方式”一起收口。

#### 7. 仅把历史项折叠还不够，生效中列表也要考虑数据增长

如果未来一个孩子同时维护很多表现项，问题不只来自历史项：

- 生效中列表本身也会变长
- 每条卡片如果信息过多，首屏仍然会显得拥挤
- 用户会在高频主区块里产生浏览疲劳

因此本期必须把“生效中项变多时的渐进展示策略”写进正式设计，而不是只处理历史项。

### 功能范围

**包含**：
- ✅ 重构表现项管理页首屏信息架构
- ✅ 把表现项按“生效中 / 待生效 / 历史项”分层展示
- ✅ 历史项默认折叠，不再和有效项混排
- ✅ 将“新建表现项”提升为明确主动作
- ✅ 将新建/编辑表单改为覆盖式编辑层，而不是页内长期直出
- ✅ 重构表现项卡片的信息层级、状态标签与动作布局
- ✅ 补齐对应页面与展示辅助逻辑测试

- ❌ 新增独立的“表现项历史页”
- ❌ 重做首页“表现记录”区块
- ❌ 扩展为全站统一设计系统改造

## 技术方案

### 方案概述

`M22G` 采用“同页收口、主流程导航统一、分层展示、覆盖式编辑、渐进展示”的方案，不新增页面路由，也不引入新的后端契约。

核心思路：

1. 保留当前 `pages/task-occurrence-edit/task-occurrence-edit` 作为唯一管理页。
2. 把页面重构为“主流程一致导航 + 上下文工具条 + 可选轻统计 + 主区 + 次级分组 + 覆盖式编辑层”。
3. 用前端展示层把现有 `items` 分成三组：
   - `生效中`
   - `待生效`
   - `历史项`
4. 历史项默认折叠，只有用户主动展开时才进入主视野。
5. 新建和编辑共用同一套表单，但不再以页内插入方式承载，而改为同页覆盖式面板。
6. 生效中列表在数量较多时，也采用渐进展示，不让主区块无限向下膨胀。
7. 页面视觉上强化“当前有效项”和“主动作”，弱化历史项和低频说明文字。
8. 明确保存、取消、停用后的回位与折叠保持规则，保证页面稳定。

### 实施结果（2026-04-22）

本期已按设计目标完成实施，当前落地结果如下：

1. 表现项管理页已切为“蓝色主流程导航 + 当前孩子工具条 + 生效中主区 + 其他表现项次级容器 + 覆盖式编辑层”的正式结构。
2. `生效中 / 待生效 / 历史项` 三类语义已由展示 helper 统一建模，页面不再自行拼装卡片状态与摘要。
3. 编辑层已改为覆盖式承载，新建和编辑不再把表单长期插入列表流中。
4. 长期有效场景下，时间区固定保留开始日期与结束日期两行，结束日期在开启长期有效时显示 `未设置`，避免重复语义和切换跳动。
5. 顶部解释型文案、过渡性 hero 结构、重复摘要表达和厚控件视觉已清理，页面已进入可交付状态。

### 关键设计决策

#### 决策1：不新增新页面，继续复用表现项设置页

本期不拆出独立的“表现项历史页”或“表现项编辑页”。

原因：

- 当前能力规模还不需要再增加路由复杂度
- 既有设计从 `M21L` 起就明确“创建与维护同页闭环”
- 真正的问题是页内信息结构，而不是入口数量不足

因此本期继续保留：

- 路由不变：`pages/task-occurrence-edit/task-occurrence-edit`
- 数据来源不变：`taskService.getOccurrenceTasks(... includeInactive: true)`

#### 决策2：新建/编辑动作前移，但顶部必须回归主流程导航语言

本期对“顺序是否要把编辑/新建往前提”的正式结论是：

- **要把动作前移**
- **不要把表单前移到页面正文里长期占位**
- **不要把头部做成强视觉 hero 卡片**
- **不要把顶部做成解释页面布局的说明区**
- **不要因为使用自定义导航，就做出与主流程割裂的另一套页头**

具体做法修订为：

- 页面顶部拆成两层：
  - 品牌一致导航：继续由页面自定义承接返回行为，但视觉语气对齐主流程页
  - 上下文工具条：承载当前孩子上下文和主按钮 `新建表现项`
- 若存在多个孩子：
  - 工具条继续显示当前选中的孩子
  - 孩子切换入口以下方独立切换条承载
  - 不把“当前孩子”和“切换控件”混成一个重交互头部组件
- 每张卡片继续保留 `编辑`
- 但新建/编辑后的表单不在列表上方或列表中间插入
- 改为以**全屏轻面板**的覆盖式方式承载
- 顶部不再额外承担“解释为什么这样排版”的职责

原因：

- 用户进入页面后，最先需要的是“看当前有哪些表现项”和“知道如何新建”
- 用户并不需要一上来就看到完整表单
- 把动作前移可以提升可发现性
- 把表单留在覆盖层里可以避免重排、跳动和首屏拥堵
- 顶部职责越纯，整页越容易显得极简、稳、自然
- 进入这页的人大多来自 `任务管理`，顶部语气必须延续主流程，而不是像进入另一张活动页
- 多孩子时，先看到“当前是谁”，再看到“还能切谁”，比把所有信息揉成一块更清楚

因此本期判断修订为：

- **当前“新建/编辑位置偏后”不合理，需要调整**
- **合理的改法不是把大表单整体搬到前面，而是把 CTA 前移，把编辑承载层从页内改成全屏轻面板**
- **合理的顶部应该是“主流程一致导航 + 上下文工具条”，而不是“导航 + 说明 + 统计 + CTA”一起堆满**
- **统一的重点不在于“都用系统导航”或“都用自定义导航”，而在于用户感知上必须属于同一产品主流程**

#### 决策3：页面首屏只突出“当前有效项”，其他信息进入次级容器

页面进入后，主视区默认只强调“当前正在生效的表现项”。

表现修订为：

- 生效中列表作为首个也是唯一的主内容块
- 待生效与历史项不再作为与主区同权重的连续主区块平铺
- 首屏空状态只解释“当前没有生效中的表现项”，而不是一上来就把所有历史项灌给用户

这样用户一眼就能回答最重要的问题：

- 现在孩子有哪些表现项正在用

#### 决策4：保留三类业务语义，但不采用三段同权平铺

列表分层规则正式固定为：

1. **生效中**
   - `startDate <= today`
   - 且未结束
2. **待生效**
   - `startDate > today`
3. **历史项**
   - 已结束、已停用、已过期的配置项

展示策略修订为：

- `待生效`：进入“其他表现项”次级容器，默认折叠为摘要行，按需展开
- `历史项`：进入“其他表现项”次级容器，默认折叠，只保留单一摘要入口
- 三类业务语义继续存在，但视觉上只保留“主区 + 次级容器”两层

补充冻结：

- 次级容器正式命名为：`其他表现项`
- `其他表现项` 不是一个可继续折叠的“第四层抽屉”，而是一个固定可见的次级信息盒
- 该容器内部只承载两类子项：
  - `待生效`
  - `历史项`
- 页面首屏不再同时出现“容器摘要 + 子项摘要”两层重复入口

这样能同时满足三个需求：

- 不丢历史管理能力
- 不让历史项干扰当前维护
- 不让页面因连续纵向平铺多个区块而显得越拉越长

#### 决策5：历史项统一用单一摘要入口，不再制造重复结构和虚构细分

当前页面把结束项直接逐条标成 `已停用`，并容易出现“标题区 + 摘要行 + 查看动作”这种重复入口。  
本期修订为：

- 首层先归为“历史项”
- 项内不再继续细分“手动停用 / 自然结束 / 其他历史来源”这类当前无稳定事实字段支撑的状态
- 历史项卡片统一使用单一弱化标签：`历史项`
- 历史项在折叠态只保留一个摘要入口，不再重复出现表达同一动作的多层结构

进一步冻结“其他表现项”容器交互：

- 容器标题固定为：`其他表现项`
- 容器本身不承担展开/收起动作，只承担分组承载和视觉降层
- `待生效` 与 `历史项` 各自拥有独立摘要入口
- 用户点击子项摘要入口时，直接展开对应子列表
- 不再出现单独一个 `查看` 文案按钮
- 如果仅存在 `待生效` 或仅存在 `历史项`，容器内只展示对应那一条摘要入口
- 如果两者都为空，则整个 `其他表现项` 容器不渲染

首层信息架构只关心：

- 现在要看的
- 未来要生效的
- 已经过去的

不让更细的状态词汇在首屏就抢主语义，也不要求实现者去猜数据库里并不存在的业务事实。

#### 决策6：新建/编辑表单采用全屏轻面板，不再使用页内展开

当前如果只是把表单改为“默认收起”，但依旧在页内展开，页面仍然会跳动。  
因此本期正式冻结为：

- 新建：点击头部主按钮后，拉起全屏轻面板
- 编辑：点击卡片编辑后，拉起同一套全屏轻面板
- 轻面板关闭时，底下列表保持原滚动位置
- 轻面板内完成保存、取消、删除后，再回到列表态

选择全屏轻面板而不是底部抽屉，原因是：

- 当前表单包含名称、类型、积分、开始日期、结束日期、长期有效开关，交互密度已经超过轻量抽屉的舒适范围
- 小程序日期选择器、键盘抬起与安全区处理在全屏面板里更稳定
- 全屏面板更容易做“返回关闭编辑层，而不是退出页面”的明确交互
- 这样能最大程度降低跳动感和布局抖动

全屏轻面板要求：

- 不新增新路由
- 不让底层列表重新排版
- 视觉上与当前页保持同一产品语境
- 允许未来继续扩字段而不破坏首屏稳定性

#### 决策6A：页面继续使用自定义导航承接交互，但视觉上必须拟合主流程页头

由于当前页面仍是系统导航栏页，系统左上返回无法先交给页面处理。  
要让“返回优先关闭编辑层”成为真实可实施能力，本期正式新增以下前提：

- `pages/task-occurrence-edit/task-occurrence-edit.json` 改为自定义导航栏模式
- 页面自身渲染自定义头部导航
- 当编辑层未打开时：
  - 头部返回 = 正常返回上一页
- 当编辑层已打开时：
  - 头部返回 = 优先关闭编辑层
  - 若有脏数据，先走确认弹窗

这样可以在**不新增新路由**的前提下，真正实现：

- 返回先关编辑层
- 不直接退出整个管理页
- 脏数据确认路径可控

但这次修订正式补充一个此前遗漏的限制：

- 自定义导航只解决交互接管，不代表视觉可以自由漂移
- 页头必须继承主流程页面的品牌蓝导航语义，至少在背景基调、标题区重心、返回区气质上与 `任务管理` 保持连续
- 不再采用当前这种“浅雾白独立头部 + 浅色页面主体”组合
- 用户从 `任务管理` 进入时，首屏应感知为“同一条管理链路中的下一层”，而不是“跳进另一种模板”

换言之，本期冻结的不是“轻量自定义导航”，而是“**行为自定义、视觉统一**”。
#### 决策6B：编辑层的返回、关闭与脏状态规则必须显式冻结

本期新增以下正式规则：

- 编辑层打开后，页面自定义导航返回优先关闭编辑层，不直接退出管理页
- 若表单无修改，关闭编辑层直接返回列表
- 若表单已有修改但未保存，关闭、返回、切孩子、切页面时都先弹确认：
  - `继续编辑`
  - `放弃本次修改`
- 编辑层打开时，禁止直接切换孩子；必须先处理当前草稿
- 新建态和编辑态都使用同一套脏状态判断规则

这样可以避免：

- 草稿被静默清空
- 编辑到一半写到别的孩子名下
- 用户以为自己只是“返回上一步”，结果整个页面退出

#### 决策7：页面按“主区 + 次级容器”渐进展示，不假设项目数量永远很少

为保证数据变多后体验不明显下降，本期修订后的正式结构策略为：

- 当 `生效中` 项数 `<= 6` 时：全部展开
- 当 `生效中` 项数 `> 6` 时：默认展示前 `6` 条，底部显示 `展开其余 X 项`
- 当 `待生效` 项数 `> 0` 时：在“其他表现项”容器内默认只显示 `待生效 N 项` 摘要行，点击后展开完整列表
- 当 `历史项` 项数 `> 0` 时：在“其他表现项”容器内默认只显示 `历史项 N 项` 摘要行，点击后展开完整列表
- 当用户展开后，页面保持该状态，直到本次会话离开
- 次级摘要行右侧只保留一种展开信号，不再同时出现多个重复提示

补充冻结次级容器首屏行为：

- `其他表现项` 容器默认始终展开显示其内部摘要入口
- 首屏默认看到的是：
  - 生效中主区
  - `其他表现项` 容器标题
  - 容器内的 `待生效 / 历史项` 摘要入口
- 首屏默认看不到待生效和历史项的完整卡片列表，除非用户主动展开对应子项

这里的 `6` 不是拍脑袋的视觉数字，而是当前页在常规手机首屏里，兼顾：

- 顶部导航和上下文工具条
- 至少 3-4 条完整卡片可见
- 下方还能保留“待生效 / 历史项”的入口感知

因此把 `6` 作为首版阈值冻结；如果真实使用后证明需要调整，再作为实施后的体验参数优化，而不是本期设计留白。  
`待生效` 与 `历史项` 都不再默认展开，因为它们天然属于次级信息，优先级都低于“当前有效项”。

#### 决策7A：`其他表现项` 的两个子入口是独立列表，不做总开关，也不做工具感过强的双按钮

当 `待生效` 和 `历史项` 同时存在时，页面允许出现两个独立的摘要入口。这里的正式语义是：

- 这是同一容器内的两个独立子列表
- 点击哪个，就只展开哪个
- 不是一个“总开关 + 子开关”的层级，也不是两个重复按钮

视觉规则正式冻结为：

- 每条摘要行右侧只保留一个展开符号
- 该符号只承担“可展开”的提示，不承担额外计数职责
- 计数必须写在摘要标题文本中，例如：
  - `待生效 2 项`
  - `历史项 5 项`
- 不再在右侧重复出现第二个数字
- 展开符号应优先使用更克制的折叠指示样式，不做工具感过强的大号 `+`

这样在同一屏里即使出现两个入口，用户也能理解为“两个独立分组”，而不是“页面上突然多了两个没来由的加号”。

排序规则固定为：

1. 结束日期更早的优先
2. 无结束日期的排在有明确到期日期之后
3. 同类再按最近修改时间倒序

这样即使未来项目增多，页面也不会在首屏立即失控。

#### 决策8：新建/编辑完成后必须保持页面回位稳定

当前新建表单长期展开，会持续抢占首屏注意力。  
本期改为：

- 新建成功：关闭编辑层，列表定位回新建项，并做一次轻高亮
- 编辑成功：关闭编辑层，回到原卡片位置，不重置列表滚动
- 停用成功：项目从 `生效中/待生效` 移出，进入 `历史项`，但历史项保持默认折叠，不自动弹开
- 取消编辑：直接关闭编辑层，回到原位置

补充冻结三组排序与锚点规则：

- `生效中`
  - 先按结束日期升序
  - 无结束日期排在有结束日期之后
  - 再按最近修改时间倒序
- `待生效`
  - 按开始日期升序
  - 再按最近修改时间倒序
- `历史项`
  - 按结束日期倒序
  - 无明确结束日期时按最近修改时间倒序

锚点规则：

- 新建出现在 `生效中`：定位到 `生效中` 区块对应卡片
- 新建出现在 `待生效`：定位到 `待生效` 区块并展开该区块
- 编辑后如果仍在原分组：回到原卡片
- 编辑后分组发生变化：定位到新分组中的新卡片
- 目标卡片进入 `历史项` 时，只更新 `历史项 N 项` 摘要，不自动展开历史列表

这样页面在高频操作下仍然是“稳”的，而不是每做一步都丢失上下文。

#### 决策9：卡片信息层级重排，动作区必须显式主次分离

每条表现项卡片修订为“正文三层 + 独立动作侧栏”：

1. **主信息层**
   - 标题
   - 类型标签
2. **关键信息层**
   - 生效时间说明
3. **状态信息层**
   - 星星数
   - 状态标签
4. **独立动作侧栏**
   - 主动作：`编辑`
   - 次动作：`更多`

补充冻结：

- `编辑` 与 `更多` 不再以同权文字按钮并列抢注意力
- 正文信息和动作区必须有明确分区，避免视觉散乱
- 右侧动作区的点击目标要明显大于纯文字本身，降低误触
- `编辑` 固定为可见主动作，使用轻量胶囊按钮
- `更多` 固定为 icon 入口，不再使用和 `编辑` 同等级的文字按钮
- `更多` 的实际点击热区不小于 `72rpx * 72rpx`
- 生效中、待生效、历史项卡片沿用同一套动作布局，不为历史项额外发明第二套动作语法

#### 决策9A：主按钮必须清晰，但重量要低于旧版强 CTA

`新建表现项` 仍然是当前页唯一主动作，但其视觉重量需要明确受控：

- 按钮要显眼，但不能成为整页唯一主视觉
- 按钮优先强调“可点”，而不是强调“宣传感”
- 视觉规则冻结为：
  - 不使用过重投影
  - 不使用过高饱和度与过强渐变
  - 高度、宽度略低于旧版 hero CTA
  - 视觉重量应低于“当前孩子名 + 生效中主区”的整体重心

判断标准：

- 用户第一眼仍能找到 `新建表现项`
- 但不会先被按钮夺走视线，再回头找“当前孩子是谁”“现在有哪些生效项”

#### 决策9B：列表卡片与次级容器的空间关系继续收紧，避免“空、散、悬”

本期新增两条空间层级冻结规则：

- `其他表现项` 容器在只有 1 条摘要入口时，必须收紧上下留白，避免卡片高度明显大于信息量
- 生效中卡片右侧动作区要继续降低割裂感，不再像单独贴上的工具柱

具体约束：

- `其他表现项` 标题到第一条摘要入口的间距要小于主区标题到第一张卡片的间距
- 次级摘要入口本身只保留单层行高，不再额外制造“看起来像第二张小卡片”的厚重感
- 卡片动作区优先顶对齐主信息层，而不是上下拉开成一根独立竖条
- 分隔视觉可保留，但只能是弱分隔，不能让动作区比正文更醒目

判断标准：

- 首屏只有 1 条历史项入口时，`其他表现项` 不会显得空
- 用户第一眼读到的仍然是标题和正文，不是右侧动作轨道

#### 决策9C：编辑层必须和列表页共享同一视觉语言，不允许出现“轻列表 + 厚表单”割裂

本期新增一条页面级视觉一致性原则：

- 列表页和编辑层必须属于同一套产品语气
- 列表页已经确定为：轻、薄、柔和、克制
- 编辑层不允许再通过更厚的控件、更大的胶囊、更高饱和度按钮变成另一套风格

具体冻结为：

- 编辑层表单控件整体采用**轻表单尺度**
- 不再使用 `88rpx / 92rpx / 82rpx` 这类连续偏大的厚控件组合
- 输入、日期、步进器、类别选择、底部操作按钮要落在同一尺寸体系内，而不是各自单独膨胀
- 列表页头部 CTA 与编辑层底部主按钮要保持同一品牌语气：
  - 都清晰可点击
  - 但都不走“强宣传按钮”路线

推荐的首版尺寸体系冻结为：

- `field-control-height = 76rpx`
  - 用于：文本输入、日期选择
- `segmented-control-height = 72rpx`
  - 用于：类别分段、星星步进器
- `action-button-height = 72rpx`
  - 用于：底部主次操作按钮
- `control-radius = 18rpx`
  - 用于：表单控件、分段项、步进器
- `panel-radius = 28rpx`
  - 用于：页面卡片、编辑层主卡片

这里的目标不是机械统一所有控件，而是统一“厚薄感”。用户应该感觉它们来自同一页面，而不是每一块都在争夺存在感。

实施约束补充：

- 后续样式实现与测试都应直接引用这套尺寸 token 的语义，而不是继续围绕旧值做排除式修修补补
- 若实现时发现某一控件因平台组件限制无法完全命中 token，允许做不超过 `4rpx` 的局部偏移，但必须保持整页观感仍处于同一档位

判断标准：

- 编辑层打开后，不会产生“像切到了另一个产品模块”的感觉
- 控件尺寸不再比列表页里的卡片和按钮明显大一号
- 首屏视觉焦点仍然是当前输入任务，而不是一排厚控件

#### 决策10：页面文案只允许“任务信息”和“状态信息”，不向用户解释布局

本期正式新增一条页面级文案原则：

- 允许出现的文案，只能是：
  - `任务信息`：告诉用户接下来可以做什么
  - `状态信息`：告诉用户当前是什么状态
- 不允许出现的文案，包括但不限于：
  - 解释布局逻辑
  - 解释设计意图
  - 解释“为什么页面这样排”

明确禁用的示例包括：

- `当前生效的放上面，其他项目收在次级区域`
- `先看当前生效中的项目，其他项目统一收在次级区域，页面更稳也更好找`

这些内容属于设计说明，不是用户完成任务所必需的信息。  
一旦把这类内容放进导航或头部，页面就会从“管理页”变成“系统在解释自己为什么这样设计”，这是本轮真机观感奇怪的核心原因之一。

因此页面各区域文案正式冻结为：

- 导航区：只保留页面标题，不保留副标题
- 上下文工具条：只保留当前孩子信息和主动作，不再附带解释型句子
- 统计信息：只允许标签式数字，不允许长句说明
- 主区 / 次级区：只保留区块标题、状态摘要、空态说明
- 编辑层：允许保留简短规则提示，因为那是具体操作上下文的一部分

#### 决策10C：编辑层去说明书化，导航负责模式识别，表单负责完成任务

本期正式冻结编辑层文案策略：

- 页面自定义导航已经能表达 `新建表现项 / 编辑表现项`
- 因此编辑层正文不再重复渲染：
  - `新建模式 / 编辑模式`
  - `新增一条可记录的表现项 / 更新这条表现项`
  - `创建后会自动回到新建项的位置 / 保存后会回到当前卡片附近`

编辑层正文应直接进入表单，不再使用大面积说明 banner。

允许保留的说明只剩一类：

- 与当前操作直接相关、且放在表单末尾不会抢占注意力的轻提示

不允许继续出现：

- 把“编辑模式”再解释一遍
- 把“保存后会发生什么”放成首屏主信息
- 让解释文案比第一个输入项更先被看到

#### 决策10D：长期有效场景下，时间区只允许出现一次“长期有效”语义

时间表单结构正式冻结为：

- 当 `hasNoEndDate === false` 时：
  - 显示 `开始日期 + 至 + 结束日期`
  - 下方显示 `长期有效` 开关
- 当 `hasNoEndDate === true` 时：
  - 时间行只显示 `开始日期`
  - 不再在同一行用结束位重复写 `长期有效`
  - 下方保留 `长期有效` 开关作为唯一状态入口

这样用户读到的是：

- 这条表现项从哪天开始
- 是否长期有效

而不是：

- 同一个“长期有效”被读两遍

#### 决策10E：时间区在长期有效场景下不仅要去重，还要避免“高而空”

上一轮已经解决了语义重复，但真机截图表明，长期有效场景下时间区仍然存在空间密度问题。  
因此本期继续冻结以下规则：

- 当 `hasNoEndDate === true` 时：
  - 时间区切换为**两行紧凑布局**
  - 第 1 行：字段标签后的单个日期值，独占整行宽度
  - 第 2 行：`长期有效` 文案与 `switch`，作为独立轻量开关行
  - 第 1 行高度使用 `field-control-height`
  - 第 2 行不再沿用输入框式容器，只保留轻分隔或轻背景
  - 第 1 行与第 2 行之间的垂直间距收敛到常规字段节奏，不得再形成大块空腔
- 当 `hasNoEndDate === false` 时：
  - 才使用完整双日期结构和对应的更宽布局
  - `开始日期 + 至 + 结束日期` 保持同一行
  - 下方仍显示 `长期有效` 开关行，但行间距略大于单日期场景

也就是说：

- 长期有效不是“双日期布局删掉一半”
- 而是切换为更轻、更紧凑的单日期布局

`switch` 的视觉处理正式冻结为：

- `switch` 仍保留系统控件语义，不做自绘替换
- 但所在行必须弱化成“设置行”，而不是继续伪装成一个大输入块
- 开关行内容垂直居中，左右对齐稳定
- 不允许让 `switch` 单独悬在大块留白区域里

判断标准：

- 长期有效场景下，时间区不会看起来像一个被掏空的大盒子
- 该区块的信息密度与名称、类别、星星区域保持一致

#### 决策10F：编辑层主按钮继续降噪，和列表页 CTA 保持同一品牌语气

本期新增按钮语气冻结：

- 编辑层底部主按钮仍是主动作，但不允许比列表页 CTA 更“喊”
- 不采用高饱和纯色大胶囊的宣传感表达
- 主按钮与次按钮的差异主要通过：
  - 填充色深浅
  - 字重
  - 边框/底色对比
  来体现，而不是靠体积明显做大

具体冻结为：

- 底部主次按钮高度同档
- 主按钮颜色允许比头部 CTA 更实一些，但必须仍属克制的产品主色
- 次按钮不做发灰占位块，而应保持与页面背景和表单底色一致的轻量辅助语气

判断标准：

- 用户能立即知道哪个是主动作
- 但不会被按钮本身先吸走注意力，再回头看表单内容

#### 决策10B：主区说明文案做减法，空态只保留单一信息源

本期进一步冻结区块级微文案策略：

- 在 `生效中` 区块存在真实卡片时：
  - 不再额外显示 `优先维护现在真正会出现的表现项` 这类解释型辅助句
  - 区块头只保留：
    - 标题
    - 数量型摘要，如 `当前在用 1 项`
- 在 `生效中` 区块为空时：
  - 区块头不再重复输出与空态卡同义的说明
  - 空态卡作为唯一信息源，承担：
    - 一个状态句
    - 一个下一步提示句

正式禁止的重复形式包括：

- 区块头说一次“当前没有生效中的表现项”，空态卡里再说一次
- 区块头给一条创建提示，空态卡里再给同一条创建提示

推荐语气规则：

- 区块头：短，偏状态
- 空态卡：短，偏行动
- 不让“状态 + 提示 + 解释”在同一区块里堆成三层说明书

#### 决策10A：顶部统计降为可选辅助，不再和头部、主区同权竞争

页面仍然允许提供数量感知，但统计的存在方式必须降权，并且显示规则必须固定，不能留给实现者自由判断：

- 统计不能再以“说明卡 + 统计块 + 主按钮”三者一起堆在头部区域
- 统计只作为可选辅助层存在，但“可选”仅指页面在特定状态下整体不渲染，不是指实现时可自由决定
- 显示规则正式冻结为：
  - 当已选中孩子且 `summary.totalCount > 0` 时：渲染轻统计
  - 当未选中孩子，或 `summary.totalCount === 0` 时：轻统计整体不渲染
- 统计的形式只允许是轻量标签块或区块内计数，不允许变成新的主视觉区域
- 统计不能把用户第一眼从“生效中主区”拉走

允许的统计表达为：

- `生效中 3`
- `待生效 1`
- `历史项 4`

不再允许：

- 长句式统计摘要
- 解释布局的统计说明
- 视觉重量接近主内容卡片的大块统计区

#### 决策11：页面结构固定为“主流程一致导航 + 上下文工具条 + 可选轻统计 + 主区 + 次级容器 + 覆盖式编辑层”

页面布局正式修订为六层：

1. **主流程一致导航**
   - 自定义导航栏
   - 视觉语气对齐主流程页头
   - 页面标题
2. **上下文工具条**
   - 当前孩子信息
   - 孩子切换
   - 主按钮 `新建表现项`
3. **可选轻统计**
   - 仅在已选中孩子且存在表现项数据时显示
   - 生效中计数
   - 待生效计数
   - 历史项计数
4. **主区**
   - 生效中
5. **次级容器**
   - 容器标题：`其他表现项`
   - 待生效
   - 历史项
6. **覆盖式编辑层**
   - 新建 / 编辑共用

这能同时满足：

- 顶部信息足够少
- 页面进入感和主流程保持连续
- 主动作足够明显
- 主区焦点足够单一
- 列表区不因编辑动作重排
- 长列表时页面仍然不乱
- 多孩子时“当前是谁”和“还能切谁”都清楚，但不会堆成一块

#### 决策12：列表加载、保存和刷新都要避免页面“跳”，并避免冗余结构叠补丁

本期把“页面稳定性”列为显式交付要求：

- 首次加载使用骨架态，占位高度接近最终卡片高度
- 刷新列表时保留各 section 折叠状态
- 编辑保存后只做必要区域刷新，不重新重建整个页面结构
- 不因摘要数字变化而触发头部高度突变
- 第二轮实施必须清理第一版中已失效的头部结构、重复摘要结构、过渡样式和废弃测试断言，不允许双方案并存

#### 决策12A：折叠/展开状态按当前孩子维度持有，不跨孩子串用

本期冻结为：

- `activeExpanded / upcomingExpanded / historyExpanded` 这些展示状态，按 `targetUserId` 维度分别持有
- 同一孩子在本次会话中的展开状态可保留
- 切换到另一个孩子后，按该孩子自己的默认状态重新计算
- 不把 A 孩子的展开状态直接带到 B 孩子

这样可以避免多孩子场景下的状态串用和理解混乱。

#### 决策12B：权限体验沿用 M22A 正式边界，不在本期弱化

本期明确不改 `M22A` 已冻结的治理边界：

- `viewer` 家长：不可管理表现项，进入时继续提示后返回
- `child`：不可进入表现项管理页；表现项管理仍然是家长能力
- 可管理的仅为具备相应治理权限的家长

本期做的是页面重构，不重新讨论权限放开。

#### 决策13：本期不改后端筛选接口，先用前端展示模型收口

虽然理论上可以新增服务端分组或筛选参数，但本期不做。

原因：

- 现有接口数据已足够支撑页面分层
- 当前规模下，前端分组三个 section 的复杂度可控
- 本期主要目标是快速收口信息架构，不扩散到服务契约调整

因此本期新增一个纯展示层辅助模型即可。

## 替代方案

### 方案A：继续沿用当前同页平铺结构，只微调样式

不采用。

原因：

- 这只能让页面“稍微好看一点”
- 不能解决历史项混排和表单长期抢焦点的问题
- 本质上还是旧信息架构

### 方案B：保留同页，但只把表单改成页内折叠展开

本期不采用。

原因：

- 比当前好，但仍然会带来内容区重排
- 用户在新建/编辑时仍容易感知到页面跳动
- 无法从根上解决“列表稳定性”问题

### 方案C：拆成两个页面，“表现项管理”与“历史项”分开

本期不采用。

原因：

- 对当前能力规模来说过重
- 会新增入口、路由与维护成本
- 当前真正的问题是同页分层不足，不是页面数量不够

### 方案D：改成 Tab 页签 `生效中 / 历史项 / 新建`

本期不采用。

原因：

- `新建` 本质上是动作，不是和列表并列的长期页签
- Tab 会让简单的管理页变成切页结构，反而增加理解成本
- 当前更适合“列表为主、全屏轻面板编辑”
