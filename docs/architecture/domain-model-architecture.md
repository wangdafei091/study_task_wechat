# 领域模型架构

## 架构概览

项目采用领域驱动设计(DDD)的架构风格，将业务逻辑封装在领域模型中，通过仓储层进行数据持久化，通过服务层处理复杂的业务流程。架构分为以下几个主要部分：

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│                 │     │                 │     │                 │
│     Models      │     │  Repositories   │     │    Services     │
│                 │     │                 │     │                 │
└────────┬────────┘     └────────┬────────┘     └────────┬────────┘
         │                       │                       │
         │                       │                       │
         ▼                       ▼                       ▼
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│                           Adapters                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
                              │
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│                      微信小程序底层API                            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 领域模型层 (Models)

领域模型是系统核心业务逻辑的载体，每个模型对应一个业务领域的实体，具有数据属性和业务方法。

### 主要模型

1. **任务模型 (Task)**
   - 定义任务的数据结构和基本业务逻辑
   - 包含任务状态枚举、重复类型枚举等
   - 提供任务验证、状态转换等业务方法

2. **星星模型 (Star)**
   - 定义星星的数据结构，作为系统中的积分单位
   - 包含来源类型、状态枚举等
   - 提供星星创建、验证等方法

3. **星星分组模型 (StarGroup)**
   - 用于管理不同有效期类型的星星集合
   - 提供分组操作、过期计算等方法

4. **奖励模型 (Reward)**
   - 定义奖励的数据结构和业务规则
   - 包含奖励类型、状态枚举等
   - 提供奖励兑换、验证等方法

5. **星星记录模型 (StarRecord)**
   - 记录星星的获取、消费和过期历史
   - 提供记录分析、统计等方法

## 仓储层 (Repositories)

仓储层负责领域模型的持久化操作，向上层提供数据访问接口，隐藏底层存储实现细节。

### 主要仓储

1. **基础仓储 (BaseRepository)**
   - 提供通用的CRUD操作
   - 实现缓存机制和批处理能力
   - 封装存储适配器的调用

2. **任务仓储 (TaskRepository)**
   - 负责任务实体的持久化
   - 提供任务查询、筛选等功能

3. **星星仓储 (StarRepository)**
   - 负责星星实体的持久化
   - 提供星星查询、统计等功能

4. **星星分组仓储 (StarGroupRepository)**
   - 负责星星分组的持久化
   - 提供分组统计、过期处理等功能

5. **奖励仓储 (RewardRepository)**
   - 负责奖励实体的持久化
   - 提供奖励查询、状态更新等功能

6. **星星记录仓储 (StarRecordRepository)**
   - 负责星星记录的持久化
   - 提供记录查询、统计分析等功能

## 服务层 (Services)

服务层负责处理跨实体的复杂业务流程，协调多个仓储的操作，实现业务用例。

### 主要服务

1. **星星服务 (StarService)**
   - 处理星星的获取、消费和过期等业务逻辑
   - 管理星星分组和记录
   - 处理与任务完成相关的星星奖励

2. **奖励服务 (RewardService)**
   - 处理奖励的创建、兑换和管理
   - 与星星服务协作，处理奖励兑换的星星消费

## 适配器层 (Adapters)

适配器层封装底层技术实现，提供统一的接口给上层组件，隔离外部依赖。

### 主要适配器

1. **存储适配器 (StorageAdapter)**
   - 封装微信小程序的存储API
   - 提供同步和异步操作接口
   - 实现缓存管理和命名空间隔离

## 辅助组件

### 日志工具 (Logger)

- 提供统一的日志记录功能
- 支持不同级别的日志（info, warn, error, debug）
- 记录模块名称、时间戳和详细消息

### 服务管理器 (ServiceManager)

- 提供服务实例的获取接口
- 管理现有服务与新架构的过渡
- 实现服务的懒加载和单例模式

## 领域事件

系统通过事件机制处理领域对象之间的通信，主要事件包括：

1. **任务事件**
   - 任务创建、更新、完成、删除

2. **星星事件**
   - 星星获取、消费、过期

3. **奖励事件**
   - 奖励创建、兑换、状态变更

## 迁移策略

从旧架构向新架构迁移采用渐进式方法：

1. **并行运行阶段**
   - 新架构与旧架构并行运行
   - 通过服务管理器决定使用哪个实现

2. **功能迁移阶段**
   - 逐步将旧功能迁移到新架构
   - 单元测试确保功能一致性

3. **完全迁移阶段**
   - 所有功能迁移完成后，移除旧实现
   - 完成架构更新

## 优势与改进

新架构相比旧架构具有以下优势：

1. **高内聚低耦合**
   - 领域模型封装业务逻辑，减少外部依赖
   - 通过接口隔离实现细节

2. **可测试性**
   - 业务逻辑与基础设施分离，便于单元测试
   - 可以模拟仓储层，测试服务层逻辑

3. **可维护性**
   - 清晰的层次结构，便于定位问题
   - 模块化设计，便于功能扩展

4. **性能优化**
   - 实现多级缓存机制
   - 批处理操作减少存储压力

5. **一致的错误处理**
   - 统一的日志记录
   - 标准化的错误返回格式
